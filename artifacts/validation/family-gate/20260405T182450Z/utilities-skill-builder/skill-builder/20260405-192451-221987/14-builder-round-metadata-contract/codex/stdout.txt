## Explicit Iteration Round Contract (one non-trivial round)

Use contract ID **`skill-hardening-round-v1`** for every non-trivial `skill-builder` hardening pass. This defines one complete evidence-bearing iteration loop from prep to handoff decision.

### Baseline rules
1. Before the round starts, choose exactly one `baseline_type` and persist it in the round manifest:
   - `no_skill` for new skills (default),
   - `prior_skill_snapshot` for existing skills,
   - `neutral_repo_baseline` only when explicitly approved by user.
2. Baseline and candidate must be pinned to immutable references:
   - candidate: path + git ref + prompt suite version + tool/env version snapshot,
   - baseline: path + baseline ref/commit + prior snapshot hash + lockfile/toolchain versions.
3. Baseline must run in the same `round_window_id`, with the same evaluator configuration, same model/runtime assumptions, and same artifact capture mode.
4. Baseline/ candidate execution order is fixed:
   - baseline run first when baseline is not `no_skill`,
   - candidate run second,
   - comparison uses only outputs from the same round window.
5. If baseline mismatch occurs (different prompts/tools/versions than declared in manifest), the round state is `blocked` and no decision is recorded.

### Frozen comparison inputs
Each round must include and hash exactly these inputs in a `comparison_inputs` manifest:
- `round_window_id` (UTC timestamp + short random suffix),
- `candidate_skill_path` and `candidate_git_ref`,
- `baseline_type` plus `baseline_git_ref` (or explicit `none` when `no_skill`),
- `prompt_pack_version`,
- `8+ should-trigger` and `8+ should-not-trigger` queries,
- `eval_mode` (`smoke` or `release`),
- `runner_image` / tool versions (`python`, `node`, `runtime`, `lint/eval` script revisions),
- `comparison_set_hash` computed from the concatenated frozen inputs.
The manifest must be written read-only before execution and treated as immutable until `decision_recorded`.

### Round-state vocabulary
Use only these round states, persisted per round in `result.json.state`:
- `prepared`
- `running`
- `evidence_captured`
- `reviewed`
- `decision_recorded`
- `blocked`

Allowed transitions are:
- `prepared -> running`
- `running -> evidence_captured`
- `evidence_captured -> reviewed`
- `reviewed -> decision_recorded`
- any state -> `blocked` on hard failure or contract violation

Allowed decision values (recorded only in `decision_recorded`) are:
- `iterate_again`
- `widen_eval_set`
- `ready_for_install_handoff`
- `ready_for_plugin_handoff`
- `stop_blocked`

### Metric unavailability handling
Each metric must be recorded with `metric_availability` in `result.json` as one of:
- `available`
- `unavailable_required`
- `unavailable_optional`
- `degraded`
For each metric, include `status`, `value`, and `reason` when unavailable.

Contract rules:
- If a **required** metric is `unavailable_required`, the round transitions to `blocked`.
- If an **optional** metric is `unavailable_optional`, the round may continue but must log `caveats` and add a remediation action.
- If metric status is `degraded`, round can proceed only if at least one non-degraded required metric supports a defensible decision.
- Any `comparison_incomplete` state must explicitly list which metric(s) caused incompleteness and the first unblocking step.

### Readiness-state distinctions
Readiness is separate from round state and must be written in `summary.json.readiness_state`:
- `starter_valid`: baseline defined and frozen; evidence exists but comparison quality not yet complete.
- `comparison_incomplete`: partial signal, no hard blocker; requires additional round or expanded eval set.
- `comparison_blocked`: hard blocker present (required metrics unavailable or frozen inputs violated); handoff prohibited.
- `downstream_ready`: all required gates passed, comparison complete, and downstream handoff preconditions satisfied.

Readiness to `downstream_ready` requires all of:
- `comparison_state = reviewed`
- `decision_recorded` is `ready_for_install_handoff` or `ready_for_plugin_handoff`
- no required metric unavailable,
- `ContractValidityEvidence` present,
- all required governance gates from `references/governance-contract.md` passed for the round.

### What makes this round valid
A hardening round is valid only if:
- baseline is frozen and verified,
- all frozen comparison inputs are immutable,
- round state progressed through `prepared -> reviewed`,
- `result.json` includes metric availability and state transitions,
- `summary.json` includes readiness state + caveat list,
- `scorecard` and `release_manifest` are aligned with the `downstream_ready` decision.
