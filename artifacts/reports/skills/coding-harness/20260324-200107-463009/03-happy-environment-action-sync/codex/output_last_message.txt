Harness keeps [`.codex/environments/environment.toml`](/Users/jamiecraik/dev/Agent-Skills/utilities/coding-harness/references/agent-install-guide.md) aligned by treating it as a harness-managed output of `harness init`. The canonical contract says `harness init` generates that file from the live `package.json` scripts, including a setup block for the detected package manager plus per-script action blocks with inferred icons/types. On existing repos, `harness init --check-updates` is the drift check, and `harness init --update` is the regeneration path. The important safety rule is that auto-updating is only considered safe when the file is harness-autogenerated; if the environment file is custom or user-owned, harness should not silently overwrite it. See [setup-and-commands.md](/Users/jamiecraik/dev/Agent-Skills/utilities/coding-harness/references/setup-and-commands.md) and [agent-install-guide.md](/Users/jamiecraik/dev/Agent-Skills/utilities/coding-harness/references/agent-install-guide.md).

The action groups that must always exist are the four canonical ones: `Tools`, `Run`, `Debug`, and `Test`. Harness can also add dynamic action blocks for each repo script, but those four groups are the required baseline. If the repo is missing `run`, `debug`, or `test` scripts, harness still emits explicit failing placeholder commands so those actions exist and fail loudly instead of giving a false green path.
