Use the harness cutover flow, not manual deletion. The current repo guidance is: scaffold CircleCI with `harness init`, then migrate GitHub Actions with the snapshot-based `harness ci-migrate` lifecycle so you always have a rollback path. I did not run any of this, so this is a no-execution playbook based on the repo’s current harness docs in [agent-install-guide.md](/Users/jamiecraik/dev/Agent-Skills/utilities/coding-harness/references/agent-install-guide.md) and [SKILL.md](/Users/jamiecraik/dev/Agent-Skills/utilities/coding-harness/SKILL.md), plus CircleCI’s migration and CLI docs: https://circleci.com/docs/guides/migrate/migrating-from-github/ and https://circleci.com/docs/guides/toolkit/local-cli/.

**Command flow**

Start from the target repo root, with harness already installed and the CircleCI scaffold generated:

```bash
# Optional preflight before any real run
bash scripts/codex-preflight.sh --stack auto --mode required

# 1. Preview the harness scaffold itself first
harness init --dry-run

# 2. Apply the scaffold if the repo is not already harness-initialized
harness init

# 3. Confirm the scaffold is up to date
harness init --check-updates
```

Then do the actual GitHub Actions to CircleCI migration through the harness:

```bash
# 4. Preview the CI migration only
harness ci-migrate prepare --provider circleci --dry-run

# 5. Apply the migration and create a recovery snapshot
harness ci-migrate prepare --provider circleci --apply
# Save the printed snapshot id from this command

# 6. Verify the snapshot-based migration
harness ci-migrate verify --snapshot <snapshot-id>

# 7. Finalize the cutover after verification passes
harness ci-migrate commit --snapshot <snapshot-id>
```

If you need to back out at any point before or after verification, use the same snapshot id:

```bash
# 8. Roll back to the pre-migration state
harness ci-migrate abort --snapshot <snapshot-id>
```

**What to look for at each stage**

`preview`
: `harness ci-migrate prepare --provider circleci --dry-run` should show which `.github/workflows/` files will be removed and confirm that CircleCI config already exists. If that list looks wrong, stop there.

`apply`
: `--apply` is the step that creates the recovery snapshot and switches the repo’s active CI provider to CircleCI.

`verify`
: `harness ci-migrate verify --snapshot <snapshot-id>` is the harness-native check that the cutover completed cleanly.

`commit`
: `harness ci-migrate commit --snapshot <snapshot-id>` seals the migration once verification is good.

`rollback`
: `harness ci-migrate abort --snapshot <snapshot-id>` restores the pre-migration state from the snapshot.

**Important guardrails**

Do not manually delete `.github/workflows/`. The harness docs are explicit that CI removal should go through `harness ci-migrate` so rollback stays available.

Do not pass `--ci circleci` to `harness init`. The current harness guidance says that flag shape is wrong for this flow and can be interpreted as a target directory instead.

After the migration, the repo should be using `.circleci/config.yml` as the CI source of truth, and the harness-managed files such as `harness.contract.json` and `.harness/ci-required-checks.json` should reflect CircleCI.
