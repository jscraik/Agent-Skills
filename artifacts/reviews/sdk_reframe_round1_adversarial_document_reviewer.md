- Why this is risky: RF-1 is scoped to doctor contract fixture/assertion work for `context7` ([.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:119](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:119), [.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:127](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:127)), but this gate couples RF-1 completion to a separate strategy document structure check. ### High - The “reversible” claim for RF-1 is under-specified and can hide production behavior drift
- Evidence: RF-1 is declared reversible by removing fixture/tests “without changing runtime behavior” ([.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:121](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:121), [.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:137](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:137)).
- Why this is risky: asserting status precedence and required fields almost always requires behavior-level normalization in doctor output ([.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:127](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:127), [.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:135](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:135)). If behavior changes are introduced, deleting tests is not a safe rollback and can silently preserve drift.
- Requested change: define RF-1 reversal proof explicitly (for example: pinned before/after command snapshots for `skills doctor context7`, plus a zero-diff or tolerated-diff contract) so rollback can be objectively verified.

### Medium - Load-bearing assumption that `context7` is representative is not falsifiable in RF-1
- Evidence: the plan chooses `context7` as first slice because it is “non-mutating” and has useful contradictions ([.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:22](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:22), [.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:119](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:119), [.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:279](/Users/jamiecraik/dev/agent-skills/.harness/reframes/2026-05-17-agent-skills-skill-sdk-doctor-trust-reframe.md:279)).
- Why this is risky: this is the load-bearing decision for the whole migration, yet there is no explicit falsification criterion for when `context7` is too atypical and RF-1 evidence cannot generalize to HE/factory skills. Without that, RF-1 can pass while still failing to de-risk later phases.
- Requested change: add one representativeness check in RF-1 acceptance (for example: compare contract fields/status precedence against one additional skill class as read-only evidence, without expanding implementation scope).
