Skills SDK user lifecycle

From idea to trusted skill

A skill starts as a small useful instruction set, then becomes a secure, testable, signed, observable software package only when its risk and reuse justify the extra gates.

Product doctrine Thin surface. Strong guardrails. Durable memory. Professional output.

What the user sees first

One command explains the next move

The SDK keeps the normal author path small. The author runs skill check, gets a readable health card, fixes the next blocker, and only sees deeper controls when the skill crosses a risk boundary.

$ skill check my-skill --json --robot tier: Scripted status: Blocked next_action: Fix env allowlist missing: sandbox receipt
Skillexport-docx
Evidenceschema pass, eval pass, secret scan pass
StatusBlocked until sandbox proof exists

Full lifecycle, compressed for users

Every skill moves through eight visible states

The user sees a simple rail. The SDK quietly performs schema, security, sandbox, eval, signing, and release checks behind each state.

1 Discover Need Capture the job, evidence, domain language, and useful outcome.
2 Choose Template Minimal, scripted, plugin, or full lifecycle starting point.
3 Author Source Write SKILL.md, references, runbooks, scripts, schemas, and README.
4 Run Check Validate schema, context quality, secrets, permissions, and blockers.
5 Harden Risk Sandbox scripts, scope env vars, sign source, scan dependencies.
6 Evaluate Run internal rubrics, context evals, A/B sandbox tests, and judge checks.
7 Package Release Create signed package, receipts, changelog, install preview, rollback.
8 Operate Improve Monitor drift, incidents, stale context, updates, deprecation, archive.

Scope discipline

Start with the smallest useful SDK, not the whole platform

The SDK should preserve the strong platform vision while implementing the smallest author-facing slice first. Build contracts before dashboards, registries, marketplaces, and broad governance systems.

Rule: strong guardrails must not crush thin surface. V1 should prove schemas, risk tiers, receipts, install scopes, evals, and security adapters before expanding into platform UX.

Intent model

Skill Story and Skill Use Case connect work to user value

User stories keep skill work focused on value; use cases add scope, actors, guarantees, success paths, and failure extensions for complex or privileged skills.

Card = short SKILL.md. Conversation = decisions, questions, assumptions, and domain context. Confirmation = evals, acceptance tests, receipts, and rubrics.
Story
story.md or READMEActor, intent, outcome, risk, confirmation, and user-visible value.
Scope
skill use caseDesign scope, goal level, primary actor, stakeholders and interests, trigger, and preconditions.
Success
guaranteessuccess guarantee, minimal guarantee, main success scenario, and observable postconditions.
Failure
extensionsAlternative paths, failure conditions, blocked states, open issues, rollback, and quarantine behavior.
Smell
skill smell checkToo broad, unclear actor, weak outcome, no eval, hidden security assumption, plugin when skill would do.

Distribution model

The SDK is a standalone CLI loaded into projects and organisations

The Skills SDK should be installable as a toolchain, not only embedded in this repo. It gives teams a consistent command surface while preserving project-local policy, templates, registries, and install scopes.

Best shape: standalone CLI plus optional project config. Install once for the user or org, then run inside any repo where skills-sdk.yaml, .codex/, or skill packages define local behavior.

skills-sdkStandalone executable or package manager install for authors, agents, CI, and org tooling.
Project

Org
policy bundleOrganisation defaults for approved tools, signing identity, RBAC, install scopes, and release gates.
CI
check runnerCircleCI and GitHub Actions run the same checks with machine-readable receipts.
Agent
factory skillsAgents use the SDK through router, skill-factory, plugin-factory, and reviewer skills.

Domain and docs

Docs explain the SDK; Skill Explorer demonstrates it

The public surface should separate capability documentation from package discovery. Use your own domain for durable identity, but keep V1 as generated docs plus a static Skill Explorer rather than a full marketplace.

Recommended stack: Fumadocs + Next.js + MDX for developer docs, generated schema and CLI references, interactive diagrams, search, versioned docs, and static skill manifest pages.

Generate
docs-as-codeGenerate CLI reference, JSON Schema docs, TypeScript/Python type docs, receipt examples, package examples, and changelog pages from source.
Deploy

Defer
not marketplace v1Publisher accounts, rankings, payments, public submissions, remote install feeds, and moderation queues wait until real adoption pressure exists.

HITL visibility

Show the work, not just the result

People should feel in the loop because the SDK exposes what agents are doing, what is blocked, what evidence exists, and where human approval changes the outcome.

The interface should feel like a workbench: plan, active step, agent actions, approvals, evidence, diffs, and receipts. Hide raw logs by default, but keep them one click away.

CLI changes

Current ask commands need a Skills SDK facade

The repo already has strong lower-level commands under ask skills, ask repo, ask evals, and ask plugins. The SDK should add a thin author-facing command layer that orchestrates those commands into one health card, receipt set, and next action.

Rule: keep ./bin/ask as the repo control plane; add skill or ask sdk as the product facade for authors and agents.

Security review

Security should be an adapter stack plus a reviewer skill

A Codex Security-style plugin would be useful as the agent review layer, but deterministic scanners still need to produce receipts. Use risk tiers to decide when SAST, SCA, secrets, SBOM, IaC, container, and LLM-specific checks become blocking.

Recommended split: CodeQL/Semgrep for code, Snyk or OSV/Grype/Trivy for dependencies and containers, BetterLeaks/Gitleaks/TruffleHog for secrets, OPA for policy, and a security-reviewer skill for threat modeling and agent-specific risks.
Agent
security-reviewer skillThreat model, prompt injection, excessive agency, toxic flows, permissions, trust boundaries.
SAST
CodeQL / SemgrepStatic analysis for scripts, Python modules, shell wrappers, plugin code, and generated emitters.
SCA
Snyk / OSV / GrypeDependency and vulnerability checks with severity thresholds, waivers, and remediation receipts.
Secrets
BetterLeaks stackBetterLeaks primary candidate, with Gitleaks or TruffleHog fallback and rotation receipts.
Policy
OPA/RegoDeny-by-default decisions for install, runtime, egress, RBAC, ABAC, and authority leases.
AI
OWASP LLM checksPrompt injection, sensitive disclosure, supply chain, poisoning, excessive agency, and tool misuse.

Install placement

Users choose where a skill is installed

The SDK should preview and install skills at the right scope. Global install is useful for personal defaults, but project-level install is essential when a skill belongs to a repo, team workflow, dependency set, or project-specific trust boundary.

Rule: no silent global install. Every install shows target path, scope, source digest, permissions, projected runtime surface, rollback path, and whether the skill affects only this project or all future projects.
Global
~/.codex or ~/.agentsUser-wide skills available across workspaces, with explicit trust and update policy.
Project
./.codex/skillsRepo-local skills committed or staged with the project, isolated from unrelated workspaces.
Workspace
.agents/skillsWorkspace projection for team or local runtime surfaces, with sync and projection receipts.
Preview
install planShows files, permissions, trust, sandbox result, conflicts, and exact paths before writing.
Rollback
remove or restoreReverts projected files, lock entries, registry metadata, and runtime surfaces by receipt.

Knowledge refs

Raw sources become trusted context through an ingestion lane

Screenshots, videos, transcripts, PDFs, Markdown, and docs should enter through deterministic extraction scripts first. Skills then curate, check usefulness, detect prompt injection, and promote only proven context into references or runbooks.

Rule: scripts extract and prove; skills judge and curate. Never let raw dropped-in material become trusted skill context without provenance, quality checks, and a promotion decision.
Intake
source manifestFile type, hash, origin, owner, capture date, freshness, license, trust level, and intended skill use.
Extract
deterministic parsersDocling/MarkItDown/PyMuPDF, Tesseract OCR, ffmpeg, Whisper, scene detection, Pandoc/LibreOffice.
Normalize
canonical markdown/jsonHeadings, tables, frames, transcript segments, page refs, timestamps, screenshots, and citations.
Screen
context safety checkPrompt injection, stale claims, unsupported instructions, toxic flows, secrets, URLs, and untrusted content boundaries.
Curate
knowledge-curator skillDistills useful task knowledge, removes clutter, resolves contradictions, and writes assumptions and glossary entries.
Promote
context receiptOnly promoted refs enter the skill package, with eval coverage, freshness policy, source links, and rollback path.

SDK-owned agent helpers

Skill Factory and Plugin Factory guide every phase

The SDK should ship dedicated agent helpers so authors can create, update, install, refactor, evaluate, release, and bundle skills or plugins without exposing every low-level command.

Default rule: skills stay skills. Use plugin-factory only when the package needs host integration, MCP servers, app surfaces, lifecycle config, dependencies, or multi-skill distribution.

Eval
skill-evaluatorRuns internal rubrics, context evals, A/B sandbox comparisons, and external confirmation handoff.
Secure
