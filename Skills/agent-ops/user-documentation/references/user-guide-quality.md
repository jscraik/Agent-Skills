# User guide quality

Read for substantial onboarding, task instructions, reader review or recovery.
Adapted from the supplied Word document and technical-writer sources in [plan.md](plan.md).

## Help readers find and finish their task

Name the audience, goal, required access and first useful result early. Use
recognisable task headings rather than “Functionality”. Introduce concepts when
needed, not in writer discovery order. Add a contents list only when length needs
navigation. Avoid empty FAQs, exhaustive glossaries and ceremony for simple tasks.

For a meaningful procedure provide starting location, prerequisites, ordered
actions, expected result and likely recovery. Put conditions before the affected
action. Keep background out of the main path. Preserve exact UI labels and use
fictional examples. Explain saves, submissions, changes and deletions where they
matter; warn before consequential actions with verified recovery options.

Tabs can separate complete genuine alternatives; collapsed sections hold optional
detail. Never hide necessary prerequisites, warnings or steps. Check that hidden
content survives export. Use ordinary headings in unsupported destinations.

## Respect readers and preserve meaning

Use familiar words, direct verbs and plain British English unless house style
requires otherwise. Explain software terms without infantilising domain experts.
Avoid “simply”, blame or humour in recovery instructions. Use semantic headings,
native lists and clear table headers. Essential meaning must not depend on colour,
position, styling or images alone.

Use actual relevant screenshots for recognising controls or results. Caption their
purpose and describe essential actions in text. Preserve context to locate the
page; never present a mock-up as a working interface. Redact sensitive data without
concealing necessary task information. Identify missing captures explicitly.
Appearance or an automated check alone does not prove accessibility conformance.

## Recovery without new harm

Describe recognisable symptoms and exact messages/codes where useful. Separate
confirmed causes from possibilities. Give the lowest-risk relevant check, expected
result and verified support route. Keep missing contacts in editorial gaps, not
invented copy. Do not recommend reinstalling, clearing data, permission changes
or repeating transactions without evidence. An error does not prove nothing
changed: protect against duplicate submissions.

## Reader-outcome review

Can the intended user find the task, obtain access, recognise the starting point,
follow the next action, identify success and recover safely? Check accuracy and
usefulness, not brevity alone. Preserve qualifications and necessary repetition.
Distinguish textual review, source comparison, executed procedure, delivered-format
inspection and independent reader trial. Report limits, not imaginary passes.
