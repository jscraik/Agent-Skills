# Brainstorm Workflow Details

Load full doctrine when needed:
`Infrastructure/references/harness-engineering/he-brainstorm-doctrine.md`.

## Intake

Confirm subject. Route concrete work to `he-spec`, `he-plan`, or `he-work`.
Classify mode as `software`, `product`, `operations`, `content`, `mixed`, or
`universal`. Classify scope as `lightweight`, `standard`, `deep-feature`, or
`deep-product`.

For explicit `he-ideate` mode, require a subject before candidate generation. If
the subject is broad, name 3-5 topic axes. Check `.harness/ideate/` for a
recent overlapping artifact and ask whether to continue it before writing a new
one.

## Discovery

Ask what the user already thinks. Then clarify objective, users, value,
constraints, non-goals, risk, sources, and criteria one question at a time.
Verify repo or Linear claims before treating them as facts.

For `he-ideate`, run web research by default unless the user explicitly skips
external research. If unavailable, record the blocker and continue from internal
grounding without treating external basis as present.

## Divergence

Generate many candidates internally, critique them, and show only the strongest
2-5 survivors. Each survivor needs a `direct`, `repo`, `external`, or
`reasoned` warrant.

In `he-ideate` mode, use a many-to-few pass: generate candidates across pain,
removal, assumption break, leverage, analogy, and constraint-flip lenses; reject
duplicates, unsupported ideas, scope overruns, and ideas below the meeting bar;
then present 2-7 survivors with basis, downside, confidence, complexity, and a
short rejection summary.

## Synthesis

Before artifact writing, present `Stated`, `Inferred`, and `Out of scope`. Keep
bullets scope-level. No files, schemas, API names, or implementation detail
unless the brainstorm is explicitly technical.

## Handoff

Offer only valid routes: `he-spec`, `he-plan`, `he-work`, `he-review`, or done.
Hide plan/build when blockers remain. For every non-trivial brainstorm,
pressure-test: solve now, simplify, defer, reject, or split.
