# Brainstorm Workflow Details

Load full doctrine when needed: `Infrastructure/references/harness-engineering/he-brainstorm-doctrine.md`.

## Intake

Confirm subject. Route concrete work to `he-spec`, `he-plan`, or `he-work`. Classify mode: `software`, `product`, `operations`, `content`, `mixed`, or `universal`. Classify scope: `lightweight`, `standard`, `deep-feature`, or `deep-product`.

## Discovery

Ask what the user already thinks. Then clarify objective, users, value, constraints, non-goals, risk, sources, and criteria one question at a time. Verify repo or Linear claims before treating them as facts.

## Divergence

Generate many candidates internally, critique them, and show only the strongest 2-5 survivors. Each survivor needs a `direct`, `repo`, `external`, or `reasoned` warrant.

## Synthesis

Before artifact writing, present `Stated`, `Inferred`, and `Out of scope`. Keep bullets scope-level. No files, schemas, API names, or implementation detail unless the brainstorm is explicitly technical.

## Handoff

Offer only valid routes: `he-spec`, `he-plan`, `he-work`, `he-review`, or done. Hide plan/build when blockers remain. For every non-trivial brainstorm, pressure-test: solve now, simplify, defer, reject, or split.
