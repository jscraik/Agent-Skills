# GitHub PR Cleanup

Use this skill to turn an already-open pull request into a clean, reviewable, merge-ready state. The workflow is evidence-first: inspect the PR, classify the remaining work, apply only targeted fixes, and close with exact validation evidence.

Do not copy raw chat transcripts, reviewer prose wholesale, or private debugging history into the skill output. Preserve repeatable operating patterns only.

## When To Use

Use this skill when the user asks to:

- clean up a GitHub PR
- address unresolved review threads
- resolve stale or already-fixed PR comments
- prepare a PR for merge
- summarize what remains on a PR
- package a proven PR cleanup workflow into repeatable steps

If the user asks for a security review, CI failure investigation, or general GitHub triage, route through the more specific skill first, then return here for final cleanup.

## Inputs To Gather

Identify:

- repository owner/name
- PR number or current branch
- base branch
- current working tree status
- unresolved review threads
- open issue comments or review comments that look actionable
- failing, pending, or skipped checks
- local commits that have not been pushed
- user constraints about whether to push, comment, resolve threads, or only report

Prefer exact command output and GitHub API data over memory.

## Workflow

### 1. Establish Repo State

Run the repo’s required bootstrap or status command first if the repository defines one.

Then inspect:

```bash
git status --short
git branch --show-current
git remote -v
git log --oneline --decorate -n 12
```

If the repository requires a wrapper for operations, use it.

Record whether the working tree is clean, dirty with user changes, or dirty with your own changes.

Never revert unrelated user work.

### 2. Identify The PR

If the user gave a PR number, use it.

Otherwise infer it from the current branch:

```bash
gh pr view --json number,title,url,headRefName,baseRefName,state,isDraft,mergeStateStatus,reviewDecision
```

If GitHub connector tools are available, prefer them for PR metadata. Use `gh` when thread-level state, review threads, or check logs require it.

Capture:

- PR number and URL
- title
- draft status
- review decision
- merge state
- head and base refs

### 3. Collect Review Feedback

Fetch both flat comments and thread-level review state.

Use GraphQL for unresolved review threads when possible:

```bash
gh api graphql -f query='
query($owner:String!, $repo:String!, $number:Int!) {
  repository(owner:$owner, name:$repo) {
    pullRequest(number:$number) {
      reviewThreads(first:100) {
        nodes {
          id
          isResolved
          path
          line
          startLine
          comments(first:20) {
            nodes {
              id
              author { login }
              body
              url
              createdAt
              outdated
            }
          }
        }
      }
    }
  }
}' -F owner=OWNER -F repo=REPO -F number=PR_NUMBER
```

Also inspect issue comments and reviews:

```bash
gh pr view PR_NUMBER --comments
gh pr view PR_NUMBER --json reviews,latestReviews,comments
```

Classify each item as:

- `actionable`: still requires code, docs, tests, or PR description work
- `already-addressed`: current code appears to satisfy it
- `stale`: comment refers to changed or removed code
- `needs-user-decision`: requires product, design, or maintainer judgment
- `non-blocking`: informational or preference-only

Do not mark a thread resolved unless the evidence is clear and the user has allowed GitHub write actions.

### 4. Check CI And Required Checks

Inspect check status:

```bash
gh pr checks PR_NUMBER
```

For failures, fetch logs for the specific failing job:

```bash
gh run view RUN_ID --log-failed
```

Classify CI failures as:

- caused by this PR
- likely flaky or infrastructure-related
- unrelated existing failure
- unknown, needs more logs

Do not guess. Tie every claim to a check name, run ID, or log excerpt.

### 5. Inspect The Diff

Review the PR diff against base:

```bash
git fetch origin BASE_BRANCH
git diff --stat origin/BASE_BRANCH...HEAD
git diff --name-only origin/BASE_BRANCH...HEAD
git diff origin/BASE_BRANCH...HEAD
```

Look for:

- accidental debug output
- unrelated file churn
- generated files that should not be committed
- stale docs or tests
- review comments that no longer match the code
- missing test coverage for touched behavior
- obvious simplification opportunities

Keep fixes scoped to PR cleanup. Avoid broad refactors.

### 6. Apply Targeted Fixes

For each actionable item:

1. Confirm the exact file and behavior.
2. Make the smallest coherent change.
3. Add or update tests when the risk warrants it.
4. Preserve existing local changes not made for this cleanup.
5. Re-check the relevant diff after editing.

If multiple unrelated findings exist, group commits or notes by concern.

### 7. Validate

Run the narrowest meaningful validation first, then broader repo checks if appropriate.

Examples:

```bash
./bin/ask repo doctor --json --robot
./bin/ask repo closeout --changed --json --robot
```

Also run package-specific tests only from verified package roots.

Capture exact pass/fail evidence:

- command
- result
- important failing line if any
- reason a command could not run

Do not claim validation passed unless it actually ran and exited successfully.

### 8. Prepare PR Closeout

Before final response or PR comment, verify:

- working tree status
- changed files
- commits ahead/behind
- PR check state
- unresolved actionable threads
- remaining user decisions

Useful commands:

```bash
git status --short
git diff --stat
git log --oneline origin/BASE_BRANCH..HEAD
gh pr checks PR_NUMBER
```

### 9. Optional GitHub Actions

Only perform write actions when requested or clearly allowed:

- push commits
- update PR description
- reply to comments
- resolve review threads
- request re-review
- mark ready for review
- merge

When resolving a thread, leave a concise evidence-based reply first if that is the team norm.

Good reply pattern:

```text
Addressed in COMMIT_OR_FILE. The updated path now handles CONDITION by BEHAVIOR, and VALIDATION_COMMAND passes.
```

For stale or already-addressed comments:

```text
This appears addressed by CURRENT_FILE_OR_COMMIT. The old code path is no longer present; current behavior is COVERED_BY_EVIDENCE.
```

## Output Format

Lead with the current PR state.

Include:

- PR link and branch
- what was changed, if anything
- review threads addressed or still open
- CI/check status
- validation commands and pass/fail results
- remaining risks or decisions

Keep the final answer concise and operational.

Example final structure:

```markdown
PR cleanup is complete for #123: TITLE.

Changed:
- `path/to/file`: fixed the remaining review issue around BEHAVIOR.
- `path/to/test`: added coverage for EDGE_CASE.

Review feedback:
- Resolved 2 actionable threads.
- 1 thread remains for maintainer decision: QUESTION.

Validation:
- PASS `command`
- FAIL `command`: REASON

Current state:
- Working tree clean.
- Branch pushed to `origin/branch-name`.
- Checks are passing except `CHECK_NAME`, which is unrelated/flaky/needs follow-up because EVIDENCE.
```

## Safety Rules

- Never copy raw transcripts into skill docs or PR comments.
- Never expose private reviewer context beyond what is already in the PR.
- Never resolve review threads without evidence.
- Never revert unrelated user changes.
- Never make broad refactors during cleanup unless the user asks.
- Never mark CI as unrelated without checking logs or prior run evidence.
- Never say the PR is ready to merge if checks, review decision, or branch state contradict that.
