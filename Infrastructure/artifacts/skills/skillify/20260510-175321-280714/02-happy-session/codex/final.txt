# GitHub PR Cleanup

Use this skill when you need to clean up an existing pull request after review comments, CI failures, or follow-up findings.

## Goal

Turn a messy PR into a small, reviewable, validated change set with:

- the right feedback addressed
- unrelated changes left alone
- tests or checks run where practical
- a concise summary of what changed and what remains

## Principles

- Prefer minimal, targeted fixes.
- Preserve user-authored work and unrelated edits.
- Resolve the underlying issue, not just the symptom.
- Treat PR cleanup as a verification workflow, not a rewrite workflow.
- Keep final communication crisp and evidence-based.
- Do not copy or depend on raw transcript text. Distill the repeatable procedure instead.

## When To Use

Use this skill when:

- a PR has unresolved review comments
- the user asks to address PR feedback
- CI is failing and the failure is tied to the current PR
- a branch needs a cleanup pass before merge
- the user wants a repeatable PR-fix workflow captured as a skill

## Workflow

### 1. Orient On The PR

Collect the minimum necessary context:

- PR title and description
- open review threads and unresolved comments
- failing checks or job logs
- changed files and the likely blast radius

Identify whether the cleanup is:

- comment-driven
- CI-driven
- code-quality-driven
- a mix of the above

### 2. Classify Feedback

For each piece of feedback, decide whether it is:

- valid and actionable
- already addressed
- stale or no longer relevant
- out of scope for this PR

Prefer fixing the smallest change that satisfies the feedback.

### 3. Preserve Scope

Before editing, check for:

- unrelated user changes in the worktree
- generated files that should not be hand-edited unless necessary
- broad refactors disguised as cleanup
- duplicate fixes across multiple files

If a fix can be made in one place, do that instead of spreading the change.

### 4. Implement The Fix

When editing:

- change only the files needed
- keep naming and style consistent with the repo
- avoid opportunistic refactors
- add comments only when the code would otherwise be hard to follow

If a review comment is ambiguous, choose the least surprising interpretation and note the assumption.

### 5. Validate

Run the smallest meaningful validation set:

- targeted tests for the affected area
- lint or type checks if relevant
- any repo-specific verification command required for the touched files

If full validation is impractical, explain exactly what was checked and what remains unverified.

### 6. Summarize Clearly

Report back with:

- what was fixed
- which review threads or issues it addresses
- what validation was run
- any remaining risks, open questions, or follow-up work

## Output Format

When reporting results, prefer:

- short summary first
- bullet list of concrete fixes
- validation evidence
- remaining risks only if relevant

Example:

- Addressed review feedback about X by updating Y.
- Fixed CI failure in Z by adjusting A.
- Verified with `...`.
- Remaining risk: `...` if applicable.

## Good Habits

- Keep the cleanup atomic.
- Favor traceability over cleverness.
- Avoid silent behavior changes.
- If you need to touch multiple concerns, separate them conceptually in the explanation.
- If the PR is large, note which parts were not changed and why.

## Anti-Patterns

Avoid:

- rewriting the branch history unless explicitly asked
- bundling unrelated fixes into the cleanup
- dismissing review comments without checking them
- over-editing code that is already correct
- summarizing by repeating the raw thread text instead of extracting the actionable steps
