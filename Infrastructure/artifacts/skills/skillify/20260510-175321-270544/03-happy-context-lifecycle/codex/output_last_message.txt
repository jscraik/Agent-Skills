# PR Feedback Workflow

Use this skill when a user asks to address PR review comments, repeat reviewer feedback, requested changes, unresolved threads, CI-linked review issues, or recurring PR cleanup patterns.

## Goal

Turn PR feedback into a reliable loop:

1. Collect all actionable feedback.
2. Classify and prioritize it.
3. Implement the smallest correct fixes.
4. Validate with explicit evidence.
5. Report what changed and what remains.
6. Capture repeatable lessons for future runs.

## Inputs

Ask for or discover:

- PR URL, branch, or local diff target.
- Review source: GitHub comments, CodeRabbit, CI logs, human notes, or pasted feedback.
- Desired scope: all feedback, only blocking feedback, one reviewer, one thread, or one theme.
- Validation expectations: tests, linters, type checks, manual browser checks, or repo-specific closeout command.

## Workflow

### 1. Orient

Run repo-native status and closeout commands where available.

Prefer project wrappers over raw package commands.

Record:

- current branch
- dirty files
- PR identifier
- feedback source
- validation commands available

Do not revert unrelated user changes.

### 2. Collect Feedback

Gather unresolved review threads, inline comments, requested changes, failing checks, and pasted feedback.

Normalize each item into:

- source
- file and line, if available
- reviewer intent
- requested behavior
- severity
- dependency on other feedback
- proposed fix

Group duplicate comments by underlying issue.

### 3. Classify

Use these buckets:

- `bug`: behavior is wrong or regressed
- `test_gap`: behavior may be correct but lacks coverage
- `maintainability`: naming, structure, complexity, duplication
- `contract`: API, schema, serialization, CLI, or public interface risk
- `security`: auth, data exposure, injection, secrets, permissions
- `performance`: query count, hot paths, memory, excessive work
- `docs`: docs, comments, changelog, migration notes
- `non_actionable`: preference, outdated comment, already fixed, unclear

If feedback is ambiguous, inspect the surrounding code before asking the user.

### 4. Plan The Fix Set

Create a short checklist ordered by risk and dependency.

For each item, decide:

- accept and fix
- already fixed, verify
- reject with rationale
- defer with reason
- needs user decision

Keep the implementation scoped to the reviewed concern.

### 5. Implement

Edit canonical sources only.

Follow local project instructions, ownership boundaries, and existing patterns.

Avoid broad refactors unless the feedback explicitly requires them.

When multiple comments point to the same root cause, fix the root cause once and mention every thread it addresses.

### 6. Validate

Run the narrowest meaningful checks first, then broader closeout checks if risk warrants it.

Validation evidence should include:

- exact command
- pass/fail result
- relevant failure excerpt if failing
- whether failure is pre-existing, unrelated, or caused by the change
- manual verification notes when needed

If validation cannot run, state why and what should be run next.

### 7. Respond To Feedback

Prepare concise reply text per thread:

- what changed
- where it changed
- validation evidence
- any reason for not changing something

Avoid defensive replies. Keep responses factual.

### 8. Close Out

Summarize:

- feedback addressed
- files changed
- validation run
- unresolved items
- risks or follow-ups

If the repo has a closeout command, run it and include the result.

- stale feedback already fixed

- security-sensitive feedback

### Dry-Run Tests

Run the skill on a local branch with mocked feedback and require no writes.

Verify that it:

- preserves unrelated dirty files
- groups duplicates

- asks for clarification only when genuinely blocked
- produces exact validation commands

### Live Repo Tests

Run against a real PR in a sandbox branch.

Success criteria:

- all addressed comments map to code changes or explicit rationale
- tests and closeout commands are reported with exact pass/fail status
- no unrelated files are modified
- final summary is suitable for a PR comment

## Observation

Track each run with lightweight evidence:

- PR identifier
- feedback item count
- classification counts
- accepted / rejected / deferred counts
- validation commands and outcomes
- reopened comments
- follow-up comments after merge
- recurring reviewer themes

Use this to answer:

- Which feedback repeats?
- Which fixes frequently need a second pass?
- Which validation steps catch regressions?
- Which comments are often stale or unactionable?
- Where should project docs, tests, or templates improve?

## Adaptation

After each meaningful run, update the skill or local references when:

- the same reviewer preference appears repeatedly
- a validation command proves unreliable
- a repo-specific ownership boundary matters
- reply wording needs to match team norms
- a class of feedback should route to another skill
- a new CI or review tool becomes canonical

Adapt by changing the smallest stable instruction, fixture, or helper script. Prefer evidence from multiple runs before hard-coding a new rule.

Lead with what changed and what passed.

Include:

- addressed feedback summary
- files changed
- validation evidence
- unresolved or deferred items
- suggested PR replies when useful

Keep the final answer concise and grounded in exact paths and commands.
