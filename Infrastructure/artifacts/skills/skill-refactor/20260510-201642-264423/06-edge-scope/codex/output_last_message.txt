**Findings**

1. **High confidence: `agent-ops` is a routing category, not a single narrow execution skill.**

The category appears designed as a broad operational router: repo hygiene, validation, automation, workflow support, bootstrapping, docs, releases, hooks, CI-adjacent fixes, and completion verification all live under it.

This is useful, but it means agents need to avoid loading too much of the category at once. The right pattern is: start with `agent-ops` only when the user asks for broad operational work, then select one more specific subskill.

Confidence: **High**
Evidence: skill descriptions show `agent-ops` as “route agent operations, repo hygiene, validation, automation, and workflow support,” while many narrower skills exist for concrete actions.

2. **High confidence: this repo strongly prefers wrapper-driven validation through `./bin/ask`.**

The AGENTS instructions make `./bin/ask` the repo operation surface and explicitly say to run:

```bash
bash scripts/bootstrap-ask.sh --json
```

before requiring `./bin/ask` on a fresh checkout. They also list repo-native validation commands:

```bash
./bin/ask repo doctor --json --robot
./bin/ask repo closeout --changed --json --robot
```

Any agent-ops workflow that shells directly into package managers or ad hoc scripts at repo root would be suspect unless it first proves the relevant package root.

Confidence: **High**
Evidence: explicit AGENTS.md instructions from the prompt.

3. **High confidence: changes to skills or agent-facing docs require language and ownership checks first.**

Before changing skills, sync policy, runtime projections, or agent-facing docs, the instructions require reading:

```text
UBIQUITOUS_LANGUAGE.md
```

They also warn to edit canonical sources, not runtime projections, and point to:

```text
Docs/agents/14-path-ownership-boundaries.md
```

That makes path ownership a core guardrail for this category. Any operational skill that edits generated/runtime-projected files directly is likely misaligned.

Confidence: **High**
Evidence: explicit AGENTS.md “Root Essentials.”

4. **Medium confidence: `verification-before-completion` should probably be treated as a final gate for meaningful agent-ops work.**

The available skill list includes `verification-before-completion`, described as:

Review and validate completion claims. Use when you are about to say work is complete, fixed, passing, pushed, or ready for review.

Given the repo’s emphasis on `repo closeout`, validation evidence, and robot JSON commands, this likely belongs near the end of most non-trivial agent-ops workflows.

Confidence: **Medium**

5. **Medium confidence: there may be overlap among `docs-expert`, `agents-md`, `ubiquitous-language`, and `project-brain`.**

These all touch documentation, agent instructions, or preserved knowledge. The category likely needs careful routing so agents do not pick a heavy docs workflow for a smaller instruction cleanup task.

Suggested routing distinction:

- Use `agents-md` for scoped AGENTS.md cleanup, contradiction removal, and instruction structure.
- Use `ubiquitous-language` when terminology itself is fuzzy or overloaded.
- Use `docs-expert` when public/repo docs need evidence-backed correction.
- Use `project-brain` when writing or repairing durable `.harness` memory files.

Confidence: **Medium**
Reason confidence is not High: based on skill descriptions only, not full skill bodies.

6. **Low confidence: category size may be large enough to cause accidental over-triggering.**

The agent-ops category contains many skills with broad operational language. That can be good for discovery, but it also risks agents invoking too many skills when a task only needs one.

A possible improvement would be ensuring `agent-ops/SKILL.md` has a crisp dispatch table with “use this when / do not use this when” boundaries for each child skill.

Confidence: **Low**
Reason confidence is Low: I could not inspect the actual routing file or current wording.
