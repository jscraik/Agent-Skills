**Recommended Route**

1. **Start With A Boundary Spec**

Create or update a design artifact before touching code. The unclear parts are exactly the parts that become production incidents if they stay implicit:

- What is an `Account` in your app?
- What is a Stripe `Customer` mapped to?
- Is billing owned by user, team, workspace, organization, tenant, or account?
- Who can start checkout?
- Who can manage billing?
- Who can cancel?
- Who keeps access during failed payment, trial, cancellation, pause, or grace period?
- Which state is authoritative: Stripe subscription status, Stripe entitlement summary, or local account flags?
- What local state is persisted and why?

The key production decision: **Stripe should own billing lifecycle facts; the app should own local authorization decisions derived from those facts.**

2. **Use Stripe Subscription Webhooks As The Lifecycle Intake**

Stripe’s docs explicitly recommend using webhooks for subscriptions because much subscription activity is asynchronous. The workflow should be webhook-driven, not request/response-driven from Checkout alone.

Minimum event lane:

- `customer.subscription.created`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `customer.subscription.paused`
- `customer.subscription.resumed`
- `invoice.paid`
- `invoice.payment_failed` or invoice status equivalents used by your integration
- `entitlements.active_entitlement_summary.updated` if using Stripe Entitlements

Stripe’s subscription webhook docs call out subscription status transitions such as `trialing`, `active`, `incomplete`, `past_due`, `canceled`, `unpaid`, and `paused`, and note that access should be revoked for states like `canceled` or `unpaid`. Source: Stripe subscription webhooks docs: https://docs.stripe.com/billing/subscriptions/webhooks

3. **Treat Permissions As A Separate Internal Layer**

Do not let raw Stripe status checks leak all over the app. Route the implementation through a small internal access model:

- `billing_owner`: can manage subscription and portal sessions.
- `account_admin`: can manage account membership and probably billing if policy allows.
- `member`: can use entitled features.
- `viewer` or lower role: cannot alter billing.
- `system`: webhook processor, allowed to mutate billing projection tables.

Then define access in terms of local derived state:

- `account.billing_state`
- `account.entitlements`
- `account.access_until`
- `account.grace_until`
- `account.suspended_at`
- `account.billing_block_reason`

That gives product, auth, and billing their own clean responsibilities.

4. **Use Entitlements If Feature Access Varies By Plan**

If this workflow controls more than a simple “paid or not paid” gate, route it through Stripe Entitlements or a local equivalent with the same shape.

Stripe describes Entitlements as the way to map internal product features to Stripe products and receive updates when customers should be provisioned or de-provisioned. Source: Stripe Entitlements docs: https://docs.stripe.com/billing/entitlements

Production shape:

- Stripe product/price/subscription determines commercial package.
- Entitlement summary determines feature access.
- Local app stores the current entitlement projection.
- Authorization checks read local projection, not Stripe live on every request.
- Webhooks update the projection idempotently.

5. **Persistence Boundary**

Persist only what the app needs to make local decisions, recover from webhook replay, and audit outcomes.

Suggested tables or models:

- `billing_customers`
  - `account_id`
  - `stripe_customer_id`
  - `created_by_user_id`
  - `billing_email`
  - `livemode`
  - timestamps

- `billing_subscriptions`
  - `account_id`
  - `stripe_subscription_id`
  - `stripe_customer_id`
  - `status`
  - `current_period_start`
  - `current_period_end`
  - `cancel_at_period_end`
  - `trial_end`
  - `metadata_snapshot`
  - timestamps

- `billing_entitlements`
  - `account_id`
  - `feature_key`
  - `active`
  - `source`
  - `stripe_lookup_key` if applicable
  - timestamps

- `billing_events`
  - `stripe_event_id`
  - `event_type`
  - `account_id`
  - `processed_at`
  - `processing_status`
  - `payload_hash`
  - `error_message`

- `account_access_state`
  - `account_id`
  - `access_state`: `active`, `trialing`, `grace`, `restricted`, `suspended`, `canceled`
  - `access_until`
  - `grace_until`
  - `reason`
  - timestamps

Do not persist raw payment method details. Keep those in Stripe.

6. **Account Lifecycle State Machine**

Route the product behavior through an explicit state machine:

- `no_billing`
  - Account exists, no subscription.
  - Access depends on free tier or setup policy.

- `checkout_pending`
  - Checkout session created.
  - Do not grant durable paid access yet.

- `trialing`
  - Access granted until trial end.
  - Payment method requirement depends on product policy.

- `active`
  - Full entitled access.

- `past_due`
  - Usually keep temporary access or enter grace.
  - Notify billing owner.

- `grace`
  - Local policy window after payment trouble.
  - Must have explicit expiry.

- `restricted`
  - Core account may remain visible, paid features disabled.

- `canceled_pending_period_end`
  - Access remains until `current_period_end`.

- `canceled`
  - Paid access revoked.

- `paused`
  - No new invoices while paused; access should follow policy.

- `unpaid`
  - Access revoked unless you intentionally define a rescue path.

Stripe’s docs distinguish `past_due`, `canceled`, `unpaid`, and `paused`, so these should not collapse into one vague “inactive” state. Source: https://docs.stripe.com/billing/subscriptions/webhooks

7. **Customer Portal Lane**

Use Stripe Customer Portal for billing self-service unless the product has a strong reason to build custom subscription management UI.

Stripe’s Customer Portal supports payment method updates, invoice access, cancellation, subscription updates, and billing info management. Source: https://docs.stripe.com/billing/subscriptions/integrating-customer-portal

App-side rules:

- Only billing owner/admin can create a portal session.
- Portal session creation must verify account membership and permission.
- Return URL must be account-scoped.
- Never trust portal return as proof of billing change; wait for webhook.

8. **Implementation Ownership**

I’d split the work like this:

- **Product/spec owner:** define account lifecycle policy, grace periods, cancellation behavior, role permissions.
- **Backend owner:** webhook ingestion, persistence projection, state machine, idempotency.
- **Security/review owner:** permission checks, webhook signature validation, tenant isolation, replay safety.
- **Frontend owner:** checkout entry, billing settings page, portal entry, user-facing restricted states.
- **Data/ops owner:** audit logs, backfill/migration, reconciliation job, dashboard/reporting.

Given Jamie’s repo preferences, this should probably become an explicit issue/plan artifact before code. The phrase “production-grade billing workflow” is a red flag for needing a durable decision record, not just a handler patch.

**Acceptance Gates**

This should not be considered routed or ready to implement until these are answered:

- Billing subject is explicit: user vs account vs workspace vs organization.
- Stripe customer mapping is one-to-one and enforced.
- Role matrix exists for checkout, portal, cancellation, plan change, invoice view.
- Webhook event list is defined.
- Local persisted billing projection is defined.
- Idempotency strategy is defined using Stripe event IDs.
- Subscription state machine is documented.
- Grace/revocation policy is documented.
- Reconciliation/backfill command exists or is planned.
- Tests cover lifecycle transitions and permission denial.
- Webhook signature verification is mandatory.
- Portal return path does not mutate billing state.
- Entitlement checks go through one internal authorization surface.

**My Verdict**

Route this as **design-first backend/security work**, with Stripe webhooks and entitlements as the billing intake, local account access as the app-owned projection, and permissions enforced through a single internal authorization surface. I would not start by wiring UI buttons or adding a subscription table in isolation. The unclear lifecycle and persistence boundary are the core work.
