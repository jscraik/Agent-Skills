So the honest answer is: **strategy is the right next stage unless there is already a validated target artifact or implementation slice waiting in the repo.**

Why strategy:

- **Refactor** should come after you know what shape you are converging toward. Starting with refactor risks polishing the wrong abstraction or moving code before the desired operating model is clear.
- **Linear plan** should come after the strategic direction is stable enough to decompose into tickets. Linear is good for execution tracking, but premature if the work still needs judgment about what matters.
- **Eval** should come after there is a concrete skill/plugin/workflow version to measure, or after you have a specific hypothesis to test. Eval is strongest as a feedback loop, not as the first framing move.
- **Strategy** fits the current ambiguity: you are asking which mode should come next, which means the work likely needs prioritization, scope framing, and a decision about what evidence would justify the following stage.

My recommended sequence would be:

1. **Strategy**: decide the objective, constraints, success signal, and whether the work is product, skill quality, repo architecture, or workflow maturity.
2. **Eval**: if the strategy depends on knowing current skill/plugin quality or regression risk.
3. **Refactor**: once eval or strategy identifies the exact structural problem.
4. **Linear plan**: once the work can be sliced into clear, ordered implementation tasks.

Concrete decision rule:

```text
If the goal is unclear: strategy.
If the goal is clear but quality/risk is unknown: eval.
If the weakness is known and structural: refactor.
If the work is already understood and just needs coordination: Linear plan.
```

So my call is: **next stage = strategy**, with a short strategy pass that produces either an eval brief, a refactor brief, or a Linear-ready implementation plan.
