**Recommended Work Breakdown**

1. **Domain framing**
   Define the billing workflow in repo language:

   - account entity
   - billing owner
   - user/member/seat relationship
   - organization/workspace/team boundary, if any
   - lifecycle states
   - billing states
   - permission actors
   - persistence owner

2. **Lifecycle model**
   Produce a state machine before code:

   - created
   - trialing
   - active
   - past_due
   - suspended or restricted
   - canceled
   - scheduled_for_cancellation
   - reactivated
   - deleted or archived, if supported

   Also define transitions and who or what may trigger them:

   - user action
   - admin action
   - webhook
   - scheduled job
   - support override
   - migration/backfill

3. **Permission model**
   Make the authorization matrix explicit:

   - who can view billing
   - who can update payment method
   - who can change plan
   - who can cancel/reactivate
   - who can view invoices
   - who can manage seats
   - what agents/background jobs can do
   - what support/admin roles can override

4. **Persistence boundary**
   Decide the system of record for each class of data:

   - local account state
   - provider subscription ID
   - provider customer ID
   - plan/product mapping
   - invoice/payment history
   - entitlement snapshot
   - audit trail
   - webhook event idempotency
   - permission grants

5. **Workflow contract**
   Define command/event boundaries:

   - commands: `ChangePlan`, `CancelSubscription`, `ReactivateAccount`, `SyncBillingStatus`
   - events: `SubscriptionActivated`, `PaymentFailed`, `AccountSuspended`, `EntitlementsChanged`
   - invariants: no paid entitlement without active billing state, no cross-tenant invoice access, webhook replay is idempotent

6. **Implementation slice**
   Only after the above, pick the smallest shippable path:

   - persistence schema and migrations
   - domain service/application service
   - permission checks
   - webhook ingestion/idempotency
   - entitlement update path
   - audit logging
   - tests around state transitions and authorization

7. **Validation**
   Use repo closeout and targeted tests:

   ```bash
   ./bin/ask repo closeout --changed --json --robot
   ```

   Add package-specific test commands only from verified package roots, per `AGENTS.md`.
