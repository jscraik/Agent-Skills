Route this as a **high-risk backend billing change**, with **security and data integrity review attached**.

Recommended review path:
1. **Backend/platform owner** for the account lifecycle state machine and persistence contract.
2. **Security review** for permissions, authz boundaries, and privilege escalation risks.
3. **Billing/Stripe best-practices review** if this touches payment providers, invoices, subscriptions, or webhooks.
4. **Data migration / integrity review** if any persisted account state, entitlement flags, or billing tables change.

What I’d flag as the three must-resolve ambiguities before implementation:
1. **Account lifecycle**
   - Which states are authoritative?
   - Who is allowed to move between them?
   - What happens on retry, rollback, cancellation, or partial payment?

2. **Permissions**
   - Which actor is allowed to initiate, approve, or undo the workflow?
   - Are permissions role-based, account-scoped, or billing-scoped?
   - Is there any admin override, and is it audited?

3. **Persistence boundary**
   - What is the source of truth for billing state?
   - Which writes are transactional versus eventually consistent?
   - Which service owns the state, and what is mirrored versus derived?
