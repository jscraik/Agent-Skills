# High-Leverage Migration Refactor Program

## Purpose

This program defines a deterministic migration path for a high-leverage refactor identified by review and strategy. It is designed to be run by agents without judgment calls hidden inside implementation work.

The program must preserve existing behavior, edit canonical sources only, and produce explicit validation evidence at each step.

## Inputs

Required inputs:

- Review artifact identifying the migration target, risk, and expected leverage.
- Strategy artifact identifying the migration priority, desired end state, and rollout boundaries.
- Canonical source paths affected by the migration.
- Runtime projection paths that must not be edited directly.
- Validation commands required before and after the change.

If any required input is missing, stop before editing and report the missing input.

## Preconditions

Before making changes:

1. Read `UBIQUITOUS_LANGUAGE.md`.
2. Read `Docs/agents/14-path-ownership-boundaries.md`.
3. Read the review artifact that identified the migration.
4. Read the strategy artifact that selected the migration.
5. Run:

```bash
./bin/ask repo doctor --json --robot
```

6. Capture the current git state:

```bash
git status --short
```

Do not proceed if the worktree contains unrelated changes in files the program intends to edit unless the changes are understood and preserved.

## Migration Selection

Select exactly one migration candidate.

A migration qualifies as high leverage when it satisfies all of the following:

- It removes repeated agent-facing guidance, duplicated policy, or divergent workflow behavior.
- It has a clear canonical source of truth.
- It can be applied mechanically across affected files.
- It has bounded validation evidence.
- It reduces future drift between authoring, validation, discovery, or runtime projections.

Record the selected migration in this form:

```text
Migration:
Canonical source:
Affected paths:
Runtime projections:
Expected leverage:
Primary risk:
Validation commands:
Rollback approach:
```

## Deterministic Rewrite Rules

Define rewrite rules before editing.

Each rule must include:

- Match condition.
- Target paths.
- Replacement behavior.
- Files explicitly excluded.
- Validation evidence.

Example rule format:

```text
Rule R001:
Match:
Replace with:
Apply to:
Exclude:
Validate with:
```

Rules must be deterministic. Avoid prose instructions such as “clean up similar wording” unless converted into exact match and replacement rules.

## Execution Phases

### Phase 1: Inventory

List all candidate files using repository tooling.

Recommended commands:

```bash
rg --files
rg "<migration-specific-pattern>"
```

Create an inventory table:

```text
Path | Ownership | Match count | Action | Notes
```

Actions are:

- `edit`
- `skip-owned-elsewhere`
- `skip-runtime-projection`
- `manual-review`
- `no-op`

### Phase 2: Dry Run

Before editing, produce the proposed changes as a dry-run plan:

```text
Rule | Path | Before | After | Risk
```

Stop if any path is marked `manual-review`.

### Phase 3: Apply

Apply only the approved deterministic rules.

Constraints:

- Edit canonical sources only.
- Do not edit runtime projections directly.
- Do not combine unrelated cleanup.
- Preserve existing formatting unless the rewrite rule requires a change.
- Keep terminology aligned with `UBIQUITOUS_LANGUAGE.md`.

### Phase 4: Regenerate

If the migration affects generated or runtime-projected content, regenerate it through the repo’s canonical wrapper rather than direct edits.

Use the appropriate `./bin/ask` command for the affected surface.

### Phase 5: Validate

Run validation in this order:

```bash
./bin/ask repo doctor --json --robot
./bin/ask repo closeout --changed --json --robot
```

If the migration affects a skill, also run:

```bash
./bin/ask skills explain <handle> --json --robot
./bin/ask skills prove <handle> --json --robot
```

Record pass/fail evidence exactly.

## Acceptance Criteria

The migration is complete when:

- The selected canonical source contains the intended policy or workflow.
- Duplicate or divergent guidance has been removed or redirected.
- Runtime projections were regenerated, if applicable.
- No runtime projection was edited directly.
- All changed files are listed with rationale.
- Required validation commands pass or failures are explained with exact output.
- `./bin/ask repo closeout --changed --json --robot` reports no unresolved closeout blockers.

## Failure Handling

If validation fails:

1. Classify the failure as migration-caused, pre-existing, or environmental.
2. Fix migration-caused failures inside the same deterministic rule set where possible.
3. Do not broaden scope to unrelated refactors.
4. If the failure requires strategy input, stop and report:
