# Repo-Wide Refactor Program

## Objective

Create a focused, evidence-driven refactor program for `agent-skills` that reduces instruction drift, clarifies canonical ownership, and makes skill/runtime behavior easier to validate without expanding scope into broad rewrites.

This program treats the upstream strategy sample as weak input, not authority. Priority is set by repo-wide leverage: changes that reduce future agent error, prevent projection/source confusion, and improve validation confidence come first.

## Priority 1: Canonical Source and Projection Boundaries

### Problem

The repo contains canonical skill/operator/docs sources and runtime projections. Agents can accidentally edit generated or projected files when the intended change belongs in the canonical source.

### Goal

Make ownership boundaries mechanically obvious and easy to validate.

### Work

- Audit all paths mentioned in `AGENTS.md`, `UBIQUITOUS_LANGUAGE.md`, and `Docs/agents/14-path-ownership-boundaries.md`.
- Produce a single canonical ownership map for:
  - skill source files
  - runtime projections
  - operator docs
  - sync policy
  - generated artifacts
- Add or tighten validation that flags edits to runtime projections when the matching canonical source should have changed.
- Ensure `./bin/ask repo closeout --changed --json --robot` reports ownership-boundary violations clearly.

### Acceptance Criteria

- A changed projected/runtime file can be traced to its canonical owner.
- Repo closeout identifies wrong-side edits in robot-readable output.
- Docs use the same terms as `UBIQUITOUS_LANGUAGE.md`.

## Priority 2: Instruction Map Normalization

### Problem

Agent-facing guidance is spread across multiple docs. Some instructions are likely stale, duplicated, or contradictory, which raises execution risk for repo-wide work.

### Goal

Make the instruction map smaller, sharper, and internally consistent.

### Work

- Start from `Docs/agents/README.md` and classify every linked agent doc as:
  - required operating contract
  - policy reference
  - validation reference
  - cleanup candidate
- Use `Docs/agents/05-contradictions-and-cleanup.md` as the backlog for stale or contradictory guidance.
- Fold duplicated guidance into the most canonical document.
- Keep `AGENTS.md` as a short routing layer, not a full policy body.

### Acceptance Criteria

- Every major instruction has exactly one canonical home.
- `AGENTS.md` links to policy rather than duplicating long policy.
- Contradiction cleanup items are either resolved or converted into explicit follow-up tasks.

## Priority 3: Skill Lifecycle Validation

### Problem

### Goal

  - source syntax/shape errors
  - policy violations
  - projection drift
  - proof failures
  - missing evidence

### Acceptance Criteria

- A skill change has an explainable path from source edit to proof evidence.
- Robot output is stable enough for agents to consume without prose scraping.
- Missing proof evidence fails loudly.

## Priority 4: Repo Doctor and Closeout Reliability

### Problem

The repo depends on wrapper commands for agent-safe operations. If `repo doctor` or `repo closeout` is noisy, incomplete, or ambiguous, agents will make poor decisions.

### Goal

Make the repo wrappers the trusted final authority for readiness and changed-file validation.

### Work

- Audit:
  - `./bin/ask repo doctor --json --robot`
  - `./bin/ask repo closeout --changed --json --robot`
- Ensure each command emits:
  - stable status
  - failing check IDs
  - actionable paths
  - clear remediation hints
  - distinction between warnings and blockers
- Remove or downgrade checks that are advisory but currently look blocking.
- Promote high-confidence ownership and validation failures to blockers.

### Acceptance Criteria

- Agents can decide pass/fail from JSON without interpreting prose.
- Changed-file closeout catches the common classes of invalid repo edits.
- Doctor output is concise enough to include in implementation evidence.

### Problem

### Goal

Use `UBIQUITOUS_LANGUAGE.md` as the terminology source of truth across agent docs and command outputs.

### Work

### Acceptance Criteria

- Skill handles and runtime/projection terms are consistently described.

  - files allowed to change

### Acceptance Criteria

- Each refactor has explicit validation evidence.
