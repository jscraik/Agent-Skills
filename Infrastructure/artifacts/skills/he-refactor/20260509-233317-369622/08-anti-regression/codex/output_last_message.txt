Here is the definition I would add.

```md
## Post-Migration Reintroduction Guardrails

After the migration, future agents must not reintroduce legacy patterns that the
migration intentionally removed. Treat these as regressions, even when they seem
like a quick local fix.

Do not reintroduce:

- Runtime projection edits as source changes.
  Edit canonical sources only. Generated, synced, projected, cached, or runtime
  copies must not become the place where behavior, policy, or user-facing agent
  instructions are authored.

- Duplicate policy copies.
  Do not copy the same rule into multiple skill, plugin, runtime, or docs
  locations unless the ownership docs explicitly require that projection. Prefer
  one canonical source plus generated or linked consumers.

- Legacy skill layouts or aliases.
  Do not restore pre-migration skill directory structures, retired handles,
  compatibility shims, or alias files unless a current canonical migration note
  explicitly says they are still supported.

- Ad hoc discovery metadata.
  Do not recreate hand-maintained registries, marketplace entries, indexes, or
  availability metadata when those are now generated, synced, or owned by a
  specific canonical source.

- Root-level package-manager workflows.
  The repository root has no package-manager install step. Do not add root
  package commands, lockfiles, dependency manifests, or install instructions as
  a convenience unless the root tooling policy is intentionally changed.

- Direct calls that bypass repo wrappers.
  Do not replace documented `./bin/ask ... --json --robot` workflows with
  package-local commands, bespoke scripts, or manual command sequences unless
  working inside a verified package root and the tooling policy allows it.

- Stale terminology.
  Do not bring back pre-migration names for concepts, paths, handles, lifecycle
  stages, or ownership boundaries. Use `UBIQUITOUS_LANGUAGE.md` as the source of
  truth.

- Mixed ownership edits.
  Do not make one change that updates canonical sources, runtime projections,
  generated caches, and consumer artifacts as if they were all peer-owned files.
  Respect path ownership boundaries and let the prescribed sync/projection step
  update derived outputs.

- Compatibility comments that preserve removed behavior.
  Do not add comments, TODOs, or fallback code that instruct future agents to keep
  supporting the old migration shape. If legacy support is still required, it
  must be documented as an active compatibility contract with an owner and an
  exit condition.

- Unvalidated migration shortcuts.
  Do not mark migration cleanup complete without running the repo’s documented
  validation or closeout commands, or recording why validation could not run.
```
