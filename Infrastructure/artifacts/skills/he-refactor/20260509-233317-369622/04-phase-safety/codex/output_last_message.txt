Here’s a ready-to-drop structure you can use for the migration section. It breaks the work into explicit phases, each with rollback conditions and eval proof requirements.

```md
## Migration Plan

The migration should proceed in bounded phases. Each phase must produce eval proof before the next phase begins, and each phase must have a defined rollback condition. A phase is not complete until its proof artifacts are attached to the migration record.

### Phase 0: Baseline and Freeze

Goal: establish the current behavior, ownership boundaries, and validation baseline before changing migration-sensitive files.

Scope:
- Identify canonical source paths and generated/runtime projections.
- Capture current skill discovery, validation, and sync behavior.
- Record current failing and passing checks so migration regressions are distinguishable from pre-existing issues.
- Freeze unrelated refactors until the migration is complete.

Rollback condition:
- No code or content migration has occurred yet, so rollback is to abandon the phase and keep the current tree unchanged.
- If baseline evidence is incomplete or contradictory, stop before implementation.

Eval proof requirements:
- `./bin/ask repo doctor --json --robot`
- `./bin/ask repo closeout --changed --json --robot`
- Inventory of affected canonical files and generated/runtime projections.
- A short baseline note listing known failures, if any, with exact command output references.

Exit criteria:
- Migration scope is explicit.
- Canonical sources are identified.
- Baseline validation evidence is captured.
- Known pre-existing failures are separated from migration risk.

### Phase 1: Canonical Source Migration

Goal: migrate only the canonical source content while preserving existing runtime behavior.

Scope:
- Update canonical skill, policy, workflow, or documentation sources.
- Avoid editing runtime projections directly.
- Preserve existing handles, identifiers, schemas, and public contracts unless the migration explicitly requires a change.
- Keep compatibility shims or aliases where consumers still depend on old names or paths.

Rollback condition:
- Revert only the Phase 1 canonical-source changes if any of the following occur:
  - Skill explanation/proof output becomes invalid.
  - Discovery can no longer resolve previously valid handles.
  - Canonical/runtime ownership boundaries become ambiguous.
  - The migration requires unplanned contract changes.

Eval proof requirements:
- `./bin/ask skills explain <handle> --json --robot` for each migrated skill or workflow handle.
- `./bin/ask skills prove <handle> --json --robot` for each migrated skill or workflow handle.
- Targeted diff review showing only canonical sources changed.
- Evidence that runtime projection paths were not manually edited.

Exit criteria:
- Canonical sources contain the migrated structure.
- Existing handles still resolve, or intentional handle changes are documented with compatibility behavior.
- Skill proof passes for all affected handles, or failures are documented as pre-existing.

### Phase 2: Projection and Sync Validation

Goal: regenerate or validate derived/runtime projections through the repo’s supported sync path.

Scope:
- Run the repo-approved sync/projection command, if required by the migration.
- Confirm generated projections match canonical source intent.
- Verify no manual edits were made to generated output.
- Confirm generated diffs are expected and minimal.

Rollback condition:
- Roll back Phase 2 generated/projection changes if any of the following occur:
  - Projection output drops required metadata.
  - Runtime skill files diverge from canonical ownership rules.
  - Sync produces unrelated churn.
  - Regenerated files are not reproducible.

Eval proof requirements:
- Repo-approved sync or projection command output, using `./bin/ask` where available.
- `./bin/ask repo doctor --json --robot`
- `./bin/ask repo closeout --changed --json --robot`
- Diff summary separating canonical changes from generated projection changes.

Exit criteria:
- Runtime projections are reproducible from canonical sources.
- Generated changes are limited to expected migration output.
- Repo doctor passes, or remaining failures are documented and unrelated.

### Phase 3: Compatibility and Consumer Verification

Goal: prove existing consumers can still use the migrated skills, docs, or workflows.

Scope:
- Test old and new entry points where compatibility is required.
- Validate discovery, explanation, proof, and install/audit paths that touch the migrated content.
- Confirm docs point users and agents to canonical locations.
- Verify stale or contradictory guidance has been removed or clearly superseded.

Rollback condition:
- Roll back to the Phase 2 state, or restore compatibility shims, if any of the following occur:
  - Existing documented commands stop working.
  - Handles resolve to the wrong skill or workflow.
  - Consumers are directed to runtime projections instead of canonical sources.
  - Agent-facing docs contradict the new migration shape.

Eval proof requirements:
- `./bin/ask skills explain <old-handle> --json --robot`, where old handles must remain supported.
- `./bin/ask skills explain <new-handle> --json --robot`, where new handles are introduced.
- `./bin/ask skills prove <handle> --json --robot` for each affected handle.
- Documentation grep or closeout evidence showing stale references were removed or intentionally retained.

Exit criteria:
- Required backward compatibility works.
- New migration paths are discoverable.
- Agent-facing docs are internally consistent.
- Proof commands pass for all affected handles.

### Phase 4: Cleanup and Deprecation

Goal: remove migration scaffolding that is no longer needed after compatibility has been proven.

Scope:
- Remove obsolete references, duplicate docs, dead aliases, and temporary migration notes.
- Keep deprecation notices only where consumers still need transition guidance.
- Preserve compatibility shims until their removal criteria are met.
- Avoid broad rewrites unrelated to the migration.

Rollback condition:
- Revert cleanup changes if any of the following occur:
  - A supported handle or command disappears prematurely.
  - Documentation no longer explains how to use the migrated path.
  - Cleanup causes unrelated formatting or ownership churn.
  - Eval proof regresses from Phase 3.

Eval proof requirements:
- `./bin/ask repo doctor --json --robot`
- `./bin/ask skills prove <handle> --json --robot` for migrated handles.
- `./bin/ask repo closeout --changed --json --robot`
- Diff review showing cleanup is limited to obsolete migration artifacts.

Exit criteria:
- Temporary migration artifacts are removed or intentionally retained with dates/conditions.
- No supported workflows are broken.
- Closeout reports only expected files.
- Final validation evidence is attached to the migration record.

## Rollback Policy

Rollback should be phase-scoped. Prefer reverting the smallest completed phase that introduced the regression rather than reverting the entire migration.

Rollback is required when:
- A previously valid skill handle cannot be explained or proven.
- Canonical/runtime ownership boundaries are violated.
- Generated projections are manually edited or not reproducible.
- Repo doctor introduces new migration-caused failures.
- Consumer-facing docs point to stale, missing, or contradictory paths.
- The migration produces unrelated churn that cannot be justified by the stated scope.

Rollback may be deferred only when:
- The failure is documented as pre-existing in Phase 0.
- The failure is unrelated to the migrated paths.
- A compensating compatibility shim is added in the same phase.
- The migration owner explicitly accepts the risk with written rationale.

## Eval Proof Requirements

Every phase must include machine-readable proof where the repo supports it. Human review notes are supplemental, not a substitute for eval proof.

Required proof bundle:
- Exact command run.
- Exit status.
- Relevant JSON output or artifact path.
- Diff summary for changed files.
- Statement of whether failures are new, pre-existing, or unrelated.
- Link or reference to the migration phase being validated.

Minimum command set:
```bash
./bin/ask repo doctor --json --robot
./bin/ask skills explain <handle> --json --robot
./bin/ask skills prove <handle> --json --robot
./bin/ask repo closeout --changed --json --robot
```

For migrations touching multiple handles, run `skills explain` and `skills prove` for each affected handle.

A migration phase is blocked from promotion if proof is missing, non-reproducible, or only manually asserted.
```

The main shape I’d use is: baseline first, canonical source changes second, projection/sync third, compatibility fourth, cleanup last. That gives you a clean rollback boundary at each point and keeps eval proof tied to the thing that actually changed.
