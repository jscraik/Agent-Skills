So I can’t honestly certify the live refactor yet. Here’s the tight acceptance bar I’d use to ensure the refactor simplifies architecture without weakening eval quality or cognition quality.

**Architecture Simplification Bar**

The refactor should be considered simplifying only if it reduces at least one of these without adding compensating complexity elsewhere:

- Fewer orchestration layers between the caller and the skill/eval/cognition behavior.
- Fewer duplicated concepts, names, or schemas for the same domain idea.
- Clearer ownership boundaries between canonical skill sources, runtime projections, eval harnesses, and cognition/prompting logic.
- Less conditional routing or fewer special cases in the hot path.
- Less hidden coupling between skills, eval definitions, prompt/cognition policy, and generated runtime artifacts.
- Simpler failure modes: errors should be easier to locate and explain after the refactor.

A refactor that only moves code around, renames things, or centralizes behavior behind a larger abstraction does not count unless the resulting dependency graph and operational model are measurably simpler.

**Eval Quality Must Not Weaken**

I’d treat eval quality as preserved only if the refactor keeps all of these intact:

- Existing eval scenarios still run.
- Existing quality gates remain at least as strict.
- No rubric dimensions are silently removed, watered down, or collapsed into vague aggregate scores.
- Regression signals remain actionable: failures should still point to specific skill behavior, missing evidence, degraded instructions, or invalid outputs.
- Any changed eval outputs are explained by intentional schema or wording changes, not by lost coverage.
- Negative cases still test real failure modes, especially over-permissive behavior, unsupported claims, missing validation, and weak evidence handling.
- Token or line-budget improvements do not come from deleting important test coverage or weakening expected outputs.

**Cognition Quality Must Not Weaken**

For cognition quality, I’d look beyond passing tests. The refactor should preserve or improve the agent’s ability to reason, select the right instructions, and produce grounded work.

The refactor should preserve:

- Progressive disclosure: agents should still load only the relevant skill instructions and referenced files.
- Correct routing: skill selection should remain specific, not broad and noisy.
- Domain language: terminology from `UBIQUITOUS_LANGUAGE.md` should remain canonical.
- Evidence discipline: claims about repo state, validation, and quality should still be backed by exact commands and outputs.
- Source-of-truth discipline: changes should target canonical sources, not runtime projections.
- Failure transparency: when a validation step cannot run, the system should say that plainly.
- Instruction hierarchy: system/developer/user/AGENTS instructions must still outrank local skill text.
- Cognitive load control: merged or simplified instructions should not become dense walls that make agents less likely to follow them correctly.

A simplification is suspicious if it removes “redundant” guidance that was actually serving as a cognition guardrail, especially guidance about validation order, canonical source ownership, evidence requirements, or skill line-budget behavior.

**Review Questions I’d Apply To The Diff**

1. Did the refactor remove concepts, or just rename them?
2. Did it reduce the number of places an agent must inspect before making a safe change?
3. Are canonical sources still clearly distinguished from generated/runtime projections?
4. Are eval failures still specific enough to debug?
5. Did any rubric, scenario, negative test, or proof step disappear?
6. Did any “agent-facing” instruction become less explicit in a way that could reduce compliance?
7. Are skill routing rules still deterministic and easy to explain?
8. Do changed files remain inside the right path ownership boundaries?
9. Is there a smaller public/API surface after the refactor?
10. Can `repo closeout --changed` produce clean, specific evidence?

**Pass/Fail Standard**

I’d call the refactor good only if all three are true:

- **Architecture:** fewer moving parts or clearer ownership with no new broad abstraction that hides behavior.
- **Eval:** same or stronger scenario coverage, same or stricter assertions, actionable failures preserved.
- **Cognition:** agents still get precise, scoped, evidence-oriented instructions with no loss of routing clarity or validation discipline.
