**Linear Project**
`Harness Artifacts: Approved Execution Plan`

**Project Goal**
Convert the approved harness artifacts into implemented, validated, and documented repo changes, with each milestone gated by explicit evidence before the next stage begins.

**Operating Gates**

1. **Artifact Gate**
   Approved artifacts are identified, linked, and confirmed as the source of truth.

2. **Implementation Gate**
   Canonical sources are changed, runtime projections are left untouched unless the approved artifact explicitly requires projection work.

3. **Validation Gate**
   Repo-native validation passes with robot-readable evidence.

4. **Review Gate**
   Changes are reviewed for scope, path ownership, safety, and stale instruction cleanup.

5. **Closeout Gate**
   Final evidence is captured with changed-file summary, validation status, and unresolved follow-ups.

---

**Milestone 1: Intake And Scope Lock**

**Outcome**
A small, explicit implementation scope exists for the approved harness artifacts.

**Linear Issues**

1. **Identify Approved Harness Artifacts**
   - Locate the approved artifact set.
   - Record artifact paths, approval source, and intended downstream changes.
   - Confirm whether each artifact affects skills, sync policy, runtime projections, agent-facing docs, or workflow docs.

   **Acceptance Criteria**
   - Artifact list is complete.
   - Each artifact has an owner area and target canonical path.
   - Any ambiguity is captured as a blocker or decision.

   **Gate**
   Artifact Gate passes.

2. **Map Artifacts To Canonical Sources**
   - Read `UBIQUITOUS_LANGUAGE.md`.
   - Apply path ownership guidance from `Docs/agents/14-path-ownership-boundaries.md`.
   - Determine which files are canonical sources versus generated/runtime projections.

   **Acceptance Criteria**
   - Each proposed change maps to a canonical source file.
   - Runtime projection edits are either avoided or explicitly justified.
   - No package-root commands are assumed from the repo root.

   **Gate**
   Scope map reviewed before implementation begins.

---

**Milestone 2: Implement Approved Changes**

**Outcome**
Approved artifact changes are applied narrowly to the canonical repo sources.

**Linear Issues**

3. **Apply Harness Artifact Changes**
   - Implement the approved changes in the mapped canonical files.
   - Preserve existing user work and avoid unrelated refactors.
   - Keep terminology aligned with `UBIQUITOUS_LANGUAGE.md`.

   **Acceptance Criteria**
   - Only scoped files are changed.
   - No unrelated formatting churn.
   - New or updated instructions match the repo’s vocabulary.

   **Gate**
   Implementation Gate passes.

4. **Update Agent-Facing Docs Or Skill Sources**
   - Update affected agent-facing docs, skill definitions, or workflow guidance.
   - Remove stale or contradictory guidance only where the approved artifact calls for it.
   - Keep skill/runtime line budgets and management rules in view if skills are touched.

   **Acceptance Criteria**
   - Agent-facing behavior is clear and executable.
   - No duplicate or conflicting instructions are introduced.
   - Skill changes remain in canonical source locations.

   **Gate**
   Docs and skill-source changes reviewed for path ownership.

---

**Milestone 3: Validate And Prove**

**Outcome**
Repo-native checks prove the artifact conversion is valid.

**Linear Issues**

5. **Run Repo Doctor**
   **Command**
   ```bash
   ./bin/ask repo doctor --json --robot
   ```

   **Acceptance Criteria**
   - Command completes successfully.
   - JSON/robot output is captured in the issue.
   - Failures are triaged into blockers or follow-up issues.

   **Gate**
   Validation Gate starts.

6. **Run Relevant Skill Proofs**
   **Command**
   ```bash
   ./bin/ask skills prove <handle> --json --robot
   ```

   Use one issue or checklist item per affected skill handle.

   **Acceptance Criteria**
   - Every changed skill has proof evidence.
   - Any proof failure has an owner, reason, and next action.
   - No unproven skill change reaches closeout.

   **Gate**
   All affected handles are proven or explicitly blocked.

7. **Run Closeout Evidence**
   **Command**
   ```bash
   ./bin/ask repo closeout --changed --json --robot
   ```

   **Acceptance Criteria**
   - Changed files are listed.
   - Validation commands and outcomes are recorded.
   - Residual risks and skipped checks are explicit.

   **Gate**
   Validation Gate passes only when closeout evidence is attached.

---

**Milestone 4: Review And Ship**

**Outcome**
The conversion is ready to merge or hand off with clean evidence.

**Linear Issues**

8. **Review For Scope, Safety, And Contradictions**
   - Check changed docs against:
     - `Docs/agents/02-tooling-policy.md`
     - `Docs/agents/04-validation.md`
     - `Docs/agents/05-contradictions-and-cleanup.md`
     - `Docs/agents/13-workflow-and-safety-guidance.md`
     - `Docs/agents/17-skill-management.md`
   - Confirm no deeper `AGENTS.md` instructions were violated.

   **Acceptance Criteria**
   - No stale guidance remains in touched areas.
   - No path ownership violations.
   - No validation gap is hidden.

   **Gate**
   Review Gate passes.

9. **Prepare Merge Or Handoff Summary**
   - Summarize approved artifacts converted.
   - Summarize files changed.
   - Include validation evidence.
   - Include unresolved blockers or explicitly empty blocker list.

   **Acceptance Criteria**
   - Summary is paste-ready for PR or Linear completion.
   - Every milestone gate has pass/fail evidence.
   - Remaining follow-ups are separate Linear issues, not buried in prose.

   **Gate**
   Closeout Gate passes.

---

**Suggested Linear Structure**

Use one Linear project with four milestones:

1. `M1 Intake And Scope Lock`
2. `M2 Implement Approved Changes`
3. `M3 Validate And Prove`
4. `M4 Review And Ship`

Use these labels:

- `harness`
- `approved-artifact`
- `agent-facing-docs`
- `validation`
- `gate`
- `blocked` when needed

Use these statuses:

- `Backlog`
- `Ready`
- `In Progress`
- `Blocked`
- `In Review`
- `Done`

**Definition Of Done**

The project is done when:

- Approved artifacts are linked and mapped.
- Canonical sources are updated.
- `./bin/ask repo doctor --json --robot` has passing evidence or documented accepted failures.
- Every changed skill has `./bin/ask skills prove <handle> --json --robot` evidence where applicable.
- `./bin/ask repo closeout --changed --json --robot` evidence is attached.
- Remaining work is represented as explicit follow-up Linear issues.
