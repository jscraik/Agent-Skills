Yes. I’d decide it by asking whether the proposed domain model changes the repo’s **shared conceptual contract** or only improves naming inside one bounded area.

Given the AGENTS guidance you provided, I would treat this as a **core strategy** change when the model does any of these:

1. It introduces or redefines canonical concepts that multiple skills, docs, commands, or workflows need to share.
2. It changes how authors should think about skill lifecycle, ownership, validation, discovery, syncing, projection, or runtime behavior.
3. It affects user-facing or agent-facing language that should appear consistently across docs, CLI output, skill metadata, or policy.
4. It creates a new organizing principle for the system, for example a new layer, actor, artifact type, lifecycle stage, or governance boundary.
5. It would belong in or require updates to `UBIQUITOUS_LANGUAGE.md`, `Docs/agents/README.md`, path ownership docs, validation policy, skill management docs, or operator contracts.
6. It needs migration guidance because existing terms become deprecated, ambiguous, or actively misleading.
7. Multiple future changes would depend on this model being understood the same way.

I’d treat it as **local terminology cleanup** when it is mostly scoped to one doc, one skill, one command surface, or one implementation area, and does not change the conceptual model other contributors need to use. Typical cleanup examples:

1. Renaming inconsistent headings or local labels.
2. Replacing stale wording with the current canonical term.
3. Clarifying a paragraph without introducing a new artifact, lifecycle state, or ownership rule.
4. Making terms consistent inside one file or bounded workflow.
5. Removing duplicate or contradictory phrasing while preserving the existing model.
6. Improving examples, command descriptions, or explanatory text without changing policy.

My practical test would be:

**If another contributor would need to learn this model before safely authoring or validating skills, it belongs in core strategy. If they only need the wording corrected where they are already working, it is local cleanup.**

A sharper repo-specific decision rubric:

| Question | If Yes | If No |
|---|---|---|
| Does this define a canonical noun, actor, lifecycle state, or boundary? | Core strategy | Likely cleanup |
| Does it affect more than one owned path or generated/runtime projection? | Core strategy | Likely cleanup |
| Would `UBIQUITOUS_LANGUAGE.md` need an entry or change? | Core strategy | Cleanup unless it reveals a contradiction |
| Does it alter validation, sync, discovery, or authoring behavior? | Core strategy | Cleanup |
| Does it only replace stale wording with an already-canonical term? | Cleanup | Maybe strategy |
| Would leaving it local cause divergent future models? | Core strategy | Cleanup |

I’d also use a **promotion path** rather than forcing the call too early:

1. Start as local terminology cleanup if the change is confined.
2. Promote to core strategy if the cleanup uncovers repeated ambiguity across docs, commands, skills, or ownership boundaries.
3. Once promoted, update the canonical source first, then cascade wording changes into dependent docs.
4. Avoid introducing a new domain model only in a downstream/runtime projection.

So my default recommendation: **only put it in core strategy if it changes the shared language or decision-making model of the repository.** If it just makes one area less confusing while preserving the current concepts, keep it local and reference the existing canonical terminology.
