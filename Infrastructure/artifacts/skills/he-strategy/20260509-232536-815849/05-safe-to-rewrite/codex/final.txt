**Safe Rewrite Zones**

Future agents may rewrite these without weakening strategic direction:

1. **Runtime Projections**

   These are explicitly non-canonical.

   Examples implied by the guide:
   - Runtime skill projections
   - Agent-facing generated copies
   - Installed or materialized skill/runtime artifacts
   - Anything described by [Path Ownership Boundaries](./Docs/agents/14-path-ownership-boundaries.md) as derived rather than canonical

   Rule of thumb: if it is generated from canonical sources, agents may replace or regenerate it. They should not treat it as the source of truth.

2. **Command Implementation Internals**

   The root contract says to use:

   ```bash
   ./bin/ask
   ```

   and notes that it forwards to:

   ```text
   Infrastructure/bin/ask
   ```

   Future agents can rewrite the implementation behind repo commands if they preserve the public behavior and robot-mode contracts.

   Safe to rewrite:
   - Internal command plumbing
   - CLI dispatch code
   - JSON formatting implementation
   - Validation orchestration internals
   - Package-local command adapters

   Must preserve:
   - Root `./bin/ask` entrypoint
   - `--json --robot` behavior
   - Existing command semantics used by agents

3. **Validation Harness Internals**

   The validation system can evolve mechanically.

   Safe to rewrite:

   - Proof runners
   - Doctor checks
   - Closeout evidence collection
   - Formatting of internal diagnostics

   Must preserve the evidence flow expected by commands such as:

   ```bash
   ./bin/ask repo doctor --json --robot
   ./bin/ask skills prove <handle> --json --robot
   ./bin/ask repo closeout --changed --json --robot
   ```

   Strategic direction is weakened only if validation becomes less trustworthy, less reproducible, or less agent-readable.

**Decision Rule For Future Agents**

A future agent may rewrite a system without weakening strategic direction when all of these are true:

1. The system is **derived, local, tactical, or implementation-facing**.
2. The canonical source remains unchanged or is intentionally updated.
3. The rewrite preserves the root command contract, especially `./bin/ask` and `--json --robot`.
4. The rewrite respects path ownership boundaries.
5. The rewrite uses canonical language from `UBIQUITOUS_LANGUAGE.md`.
6. The rewrite can be proven with repo validation commands.
7. The rewrite removes duplication, stale guidance, or accidental complexity rather than changing the repo’s conceptual model.

The crisp version: **future agents may freely rewrite the machinery, projections, and tactical skill content; they should protect the vocabulary, ownership boundaries, operating contract, validation policy, and lifecycle governance.**
