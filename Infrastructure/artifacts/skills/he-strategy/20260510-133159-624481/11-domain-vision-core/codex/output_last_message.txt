Yes. I’d decide it by asking whether the proposed domain model changes the **shared conceptual contract** of the system, or whether it only makes one local area easier to read.

A proposed domain model belongs in **core strategy** when it defines vocabulary, boundaries, or relationships that multiple skills, workflows, docs, projections, or operators need to agree on. It is local terminology cleanup when it renames or clarifies concepts inside one bounded implementation area without changing how the broader system thinks.

**Core Strategy**

Treat it as core strategy if most of these are true:

1. **It names a cross-cutting concept**

   The model describes something that appears across multiple parts of the repo: skills, plugins, runtime projections, policy, sync, validation, discovery, agent workflows, or docs.

   Example signal: “Skill”, “runtime projection”, “canonical source”, “operator doc”, “validation evidence”, “sync policy”, “agent-facing contract”.

2. **It changes the ubiquitous language**

   If adopting the model would require updating `UBIQUITOUS_LANGUAGE.md`, agent docs, command help, or user-facing explanations, it is strategic.

   A good test: would two contributors misunderstand each other if one used the new model and one used the old terms? If yes, it belongs in core strategy.

3. **It affects ownership boundaries**

   If the model changes which files are canonical, generated, projected, synced, or owned by which workflow, it is not just cleanup.

   That kind of change belongs near the core strategy because it affects how agents decide where to edit.

4. **It influences validation or governance**

   If the model affects what must be proven, audited, folded, installed, synced, or rejected, it is strategic.

   Example: introducing a distinction like “draft skill” vs “published skill” vs “runtime-projected skill” would probably be core strategy if commands or validation rules depend on it.

5. **It would appear in more than one command or workflow**

   If the same model needs to be understood by `skills improve`, `skills explain`, `skills prove`, `repo closeout`, sync tooling, and documentation, it belongs in core strategy.

6. **It changes decision-making**

   If the model helps decide what should happen, not just what something is called, it is strategic.

   Example: “canonical source vs runtime projection” is strategic because it tells agents where to edit and what to avoid.

7. **It creates or formalizes system invariants**

   If the model implies rules like “every runtime projection must derive from a canonical source” or “skills must remain below a line budget unless folded,” that is core strategy.

**Local Terminology Cleanup**

Treat it as local cleanup if most of these are true:

1. **It only improves names in one file or package**

   The concept does not need to be taught globally. It just makes a specific implementation clearer.

2. **It does not alter repo-wide behavior**

   Commands, validation, ownership, sync, docs, and agent workflows keep working the same way.

3. **It has no new invariant**

   The rename does not create a rule the rest of the repo must obey.

4. **It is implementation-local**

   The term helps explain one parser, command adapter, UI label, fixture, test helper, or internal data shape.

5. **It can be reviewed as a refactor**

   If the change can be evaluated by asking “does this preserve behavior and improve clarity?”, it is probably cleanup.

6. **It does not need a migration path**

   If old terms can disappear locally without coordinated docs, projections, command output, or user education, it is local.

**The Sharp Test**

Ask this:

> If we accept this domain model, do future agents and contributors need to use it to make correct decisions across the repository?

If yes, it belongs in **core strategy**.

If no, and it only helps one area read better, it is **local terminology cleanup**.

**Practical Classification Rubric**

I’d score it like this:

| Question | If Yes |
|---|---|
| Does it affect `UBIQUITOUS_LANGUAGE.md`? | Core strategy |
| Does it change canonical-vs-generated ownership? | Core strategy |
| Does it affect validation, sync, install, audit, or closeout behavior? | Core strategy |
| Does it appear in multiple skill or repo workflows? | Core strategy |
| Does it introduce a new invariant or lifecycle state? | Core strategy |
| Is it only a rename inside one command/module/test? | Local cleanup |
| Can it ship without docs or command behavior changes? | Local cleanup |
| Would outside contributors need to learn it? | Core strategy |
| Would only maintainers of one file care? | Local cleanup |

**Decision Language I’d Use**

For a core strategy decision:

> This proposed model belongs in core strategy because it changes the shared vocabulary agents use to decide where concepts live, which sources are canonical, and what validation means. It should be reflected in the ubiquitous language and any affected agent-facing docs before implementation details are renamed around it.

For local cleanup:

> This is local terminology cleanup. The proposed names clarify one implementation area, but they do not change the shared domain contract, ownership boundaries, validation rules, or cross-workflow behavior. Keep the change scoped to the local files and avoid promoting the terms into global docs unless they recur elsewhere.

**My Default Bias**

I’d be conservative about promoting models into core strategy. A domain model earns that place only when it changes shared reasoning across the system. Otherwise, keep it local, let the terminology prove itself in code, and promote it later if it starts showing up in multiple workflows or docs.

One useful middle path is to mark it as **local vocabulary with strategic potential**: use the names in the narrow area now, but do not update `UBIQUITOUS_LANGUAGE.md` or agent-wide docs until the model affects at least two independent workflows.
