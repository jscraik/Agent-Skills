# HE Live Tracker Proof Process Spec

## Mode Decision

This spec covers a proposed Harness Engineering process for preventing local
artifact completion from being mistaken for live tracker completion.

The first-principles challenge changes the default answer: do not add a new HE
process yet. The smallest sufficient next mechanism is a reference contract plus
negative eval coverage across the existing `he-linear-plan`, `he-spec`, and
`he-eval-report` lifecycle. A new process is allowed only if that smaller
mechanism cannot make the verified failure impossible to miss.

## Scope Challenge

The verified failure is specific:

- an HE artifact can look complete while the intended live tracker mutation is
  missing, unapproved, blocked, or only represented as a ready-to-create payload;
- downstream stages can then treat local `.harness` output as equivalent to
  live Linear state;
- the user has to ask why the live issue, live tracker, or live closure state
  does not exist.

The narrowest prevention mechanism is not a new process. The failure can be
prevented if every tracker-touching HE artifact must expose:

- `linear_mutation_status`;
- `linear_action_required`;
- required confirmation or blocker text;
- a machine-readable distinction between `created`, `updated`,
  `confirmation_required`, `blocked`, `not_requested`, and `not_applicable`;
- closure rules that forbid `complete` when expected live mutation is missing.

That is a reference contract plus eval problem first. A new process would be
justified only if the failure requires recurring reconciliation work that cannot
be encoded in the existing stages.

## Problem

HE already has strong local planning, spec, review, and eval artifacts. The
trust defect appears when those artifacts describe external tracker work without
forcing the reader to know whether the external mutation actually happened.

The current lifecycle should not grow a new process unless the lower-scope
mechanism fails. A new stage would add routing surface area, more artifacts, and
more places to drift. The durable fix should first make the existing artifacts
unable to overstate live tracker state.

## Goals

- Prevent local `.harness` artifacts from implying live Linear or tracker state
  that does not exist.
- Make side-effect status explicit and machine-readable in every
  tracker-sensitive HE output.
- Prefer contract, eval, and lint enforcement over adding a new process.
- Define the strict conditions under which a new HE process becomes justified.
- Preserve user approval boundaries for live Linear creation, update, and
  closure.

## Non-Goals

- Do not create a new HE stage in this slice.
- Do not mutate Linear.
- Do not create a broad project-management workflow.
- Do not add a dashboard, queue, or full tracker synchronization service.
- Do not rewrite `he-linear-plan`, `he-spec`, or `he-eval-report`.
- Do not make every HE artifact require live tracker state.
- Do not block local-only cognition work when no external tracker was expected.

## Proposed Reference Contract

Create `Plugins/harness-engineering/references/live-tracker-proof-contract.md`.

The contract should define:

- when an HE artifact is tracker-sensitive;
- required fields for tracker-sensitive artifacts;
- allowed `linear_mutation_status` values;
- closure rules for `confirmation_required`, `blocked`, and `not_requested`;
- how to phrase ready-to-create payloads without implying they exist live;
- how `he-eval-report` should grade closure when live mutation was expected but
  not performed;
- how local-only cognition artifacts can stay valid when no external tracker is
  expected.

The contract should stay short. Deep examples belong in eval fixtures, not in
hot-path skill prose.

slice. If they cannot reliably catch the failure, the next plan may add a
deterministic lint.

## Conditional New Process

A new HE process becomes justified only if all of these are true:

- reference contract exists and is wired into the tracker-sensitive lifecycle
  stages;
- negative evals exist and are part of strict audit or release validation;
- artifact lint either exists or was explicitly rejected with evidence;
- a fresh failure still shows local artifacts drifting from live tracker state;
- the failure requires recurring reconciliation, not just better output
  contracts.

If justified later, the new process should be named around reconciliation, not
planning. Candidate shape:

- input: changed `.harness` artifacts plus live tracker ids;
- output: one reconciliation report with `live_state`, `artifact_state`,
  `mutation_status`, `closure_allowed`, and `next_action`;
- side effects: read-only by default; live mutations require explicit user
  confirmation;
- validation: negative fixtures for missing issue, stale issue, blocked
  mutation, and local-only artifact.

## Interfaces

### Tracker-Sensitive Artifact Interface

Tracker-sensitive artifacts must expose:

```yaml
linear_issue: "JSC-123 | untracked | not_applicable"
linear_status: "created | updated | not_created | not_applicable | unknown"
linear_mutation_status: "not_requested | confirmation_required | created | updated | blocked | not_applicable"
linear_action_required: true
```

If `linear_action_required: true`, the artifact must include:

- target tracker or project when known;
- proposed issue type and title when creation is needed;
- required confirmation text;
- blocker reason when mutation failed or was unavailable.

### Closure Interface

Closure claims must follow these rules:

- `created` or `updated`: live tracker closure can be considered if validation
  and PR evidence also pass.
- `confirmation_required`: local implementation may be complete, but live
  tracker closure is blocked.
- `blocked`: local and/or live closure is blocked until the blocker is removed.
- `not_requested`: local work can close only if external tracker work was never
  expected.
- `not_applicable`: valid only when the artifact is not tracker-sensitive.

### Eval Report Interface

`he-eval-report` must report tracker proof separately from implementation
proof. It should not collapse “code is done” and “live issue is closed” into
one decision.
