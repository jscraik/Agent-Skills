Here’s a clean acceptance-criteria set for **gate selection** focused on standard work recording minimum proof and skipped heavy gates.

**Acceptance Criteria: Gate Selection**

1. **Standard Work Uses Minimum Proof**
   - Given a task is classified as standard work,
   - When gate selection is performed,
   - Then the selected gate set records only the minimum proof required to support the change.
   - And the proof must be sufficient to show that the relevant behavior, file, workflow, or documentation path was checked.
   - And the proof must avoid unnecessary broad validation when the change scope does not justify it.

2. **Heavy Gates Are Skipped for Standard Work**
   - Given a task is classified as standard work,
   - When heavyweight validation gates are available, such as full test suites, broad audits, deep reviews, long-running checks, or cross-package validation,
   - Then those heavy gates are skipped unless the task scope explicitly requires them.
   - And each skipped heavy gate is recorded with a short reason.

3. **Skipped Gate Reason Is Explicit**
   - Given a heavy gate is skipped,
   - When the closeout or proof record is produced,
   - Then the skipped gate entry includes:
     - the gate name,
     - the reason it was skipped,
     - the scope signal that made the skip acceptable.
   - Example reason: `Skipped full suite because the change only updates agent-facing documentation and no executable code paths changed.`

4. **Minimum Proof Is Still Concrete**
   - Given standard work uses minimum proof,
   - When validation evidence is recorded,
   - Then the evidence must include concrete commands, checks, file paths, or inspection results.
   - And the record must not rely on vague statements such as “looks fine” or “not needed” without supporting context.

5. **Gate Selection Matches Change Scope**
   - Given a change affects only documentation, metadata, prompt text, policy wording, or non-runtime skill guidance,
   - When gate selection runs,
   - Then proof may be limited to targeted inspection, schema validation, line-budget checks, linting of the affected artifact, or the repo’s standard closeout command as appropriate.
   - And runtime, integration, or package-level tests are skipped unless the affected artifact is consumed by those paths.

6. **Escalation Happens When Risk Increases**
   - Given a standard-work task begins with minimum proof,
   - When the change is found to affect runtime behavior, generated projections, package code, sync policy, schema contracts, validation logic, or shared command behavior,
   - Then gate selection escalates to the relevant heavier gates.
   - And the proof record explains why the task no longer qualifies for minimum-only proof.

7. **Skipped Gates Do Not Hide Required Validation**
   - Given a gate is required by ownership rules, AGENTS.md guidance, repo policy, or the affected skill/document workflow,
   - When gate selection is performed,
   - Then that gate must not be skipped solely because the task is standard work.
   - And if the gate cannot be run, the record must mark it as blocked with the exact blocker instead of skipped.

8. **Closeout Summarizes Selected, Skipped, and Blocked Gates**
   - Given gate selection has completed,
   - When the final work record or closeout summary is produced,
   - Then it includes separate entries for:
     - gates run,
     - minimum proof recorded,
     - heavy gates skipped,
     - gates blocked, if any.
   - And each entry includes enough evidence for a reviewer to understand the decision without re-running discovery.

9. **Robot Output Preserves Gate Decisions**
   - Given the repo command is run with `--json --robot`,
   - When gate selection or closeout emits machine-readable output,
   - Then selected gates, skipped heavy gates, skip reasons, and proof evidence are present in stable structured fields.
   - And downstream agents can distinguish `run`, `skipped`, and `blocked` gate states.

10. **No Runtime Projection Edits Are Required for Criteria-Only Work**
   - Given the task only adds or updates acceptance criteria for gate selection,
   - When files are changed,
   - Then edits are made in the canonical source location.
   - And runtime projections are not edited directly.
   - And any generated/runtime output is updated only through the repo’s sanctioned sync or projection workflow, if required.
