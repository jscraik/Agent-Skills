**Spec: Bundled Plugin Hook for Harness Engineering Runtime Recovery**

**Status:** Proposed
**Owner:** Harness Engineering
**Decision Type:** Conditional mechanism
**Recommendation:** Do not recommend by default. Recommend only when repeated runtime evidence proves a bundled plugin hook is the smallest safe mechanism.

**Problem**

Harness Engineering workflows occasionally encounter runtime failures that are not caused by an individual skill’s written instructions, a single malformed command, or a missing validation step. Some failures recur across sessions because the runtime environment, plugin projection, or invocation boundary repeatedly enters a bad state before the agent has enough context to correct course manually.

A bundled plugin hook could intercept or prepare those runtime conditions earlier than normal skill instructions. However, hooks are powerful and implicit. They can obscure control flow, create surprising side effects, and become a broad mechanism for problems that should instead be solved with clearer instructions, narrower validation, better command contracts, or explicit workflow steps.

The purpose of this spec is to define when a bundled plugin hook is allowed, what it may do, and what proof is required before recommending it.

**Core Principle**

A bundled plugin hook is acceptable only when a repeated runtime failure proves that the hook is the smallest safe mechanism.

“Smallest safe mechanism” means:

1. The failure occurs at runtime before ordinary skill guidance can reliably prevent it.
2. The failure has repeated with materially similar symptoms across more than one run, scenario, or user workflow.
3. Narrower fixes have been considered and found insufficient.
4. The hook can be scoped to a specific plugin, workflow phase, command boundary, or runtime condition.
5. The hook’s behavior is deterministic, observable, reversible, and testable.
6. The hook does not silently change user-authored content, canonical skill sources, repo policy, or unrelated runtime state.

**Non-Goals**

This hook must not become a general-purpose policy engine.

It must not be used to:

1. Patch weak skill instructions.
2. Replace explicit validation commands.
3. Hide flaky behavior without surfacing evidence.
4. Rewrite canonical docs or skills at runtime.
5. Apply broad environment mutation for convenience.
6. Enforce subjective style or quality preferences.
7. Automatically recover from failures that should remain visible to the user.
8. Bypass ownership boundaries between canonical sources and runtime projections.

**When To Recommend**

Recommend the bundled plugin hook only when all of the following are true:

1. **Repeated failure:** The same runtime failure mode has occurred at least twice, or once in a reproducible scenario plus once in prior session evidence.
2. **Runtime-local cause:** The failure is caused by runtime setup, projection state, plugin load order, tool availability, command wrapping, or another condition that exists before normal task execution.
3. **Instruction-level fix is insufficient:** Updating skill text, AGENTS guidance, operator docs, or command examples would not reliably prevent the failure.
4. **Wrapper-level fix is insufficient:** Existing repo wrappers, `./bin/ask` commands, validators, or closeout checks cannot address the issue with equal or smaller scope.
5. **Hook scope is narrow:** The hook can be limited to a single plugin bundle, HE workflow, lifecycle event, or explicitly detectable runtime state.
6. **Behavior is auditable:** The hook emits structured evidence showing whether it ran, what condition triggered it, and what action it took.
7. **Failure remains visible:** If the hook cannot safely correct the condition, it reports a clear failure instead of continuing silently.
8. **Rollback is trivial:** Disabling the hook restores previous behavior without requiring data migration or cleanup of canonical sources.

**When Not To Recommend**

Do not recommend the hook if any of the following are true:

1. The failure is a one-off.
2. The failure is caused by unclear documentation.
3. The failure is caused by a missing test.
4. The failure is caused by an incorrect command in a skill.
5. The failure can be fixed by editing canonical skill content.
6. The failure can be fixed by improving `./bin/ask` behavior.
7. The hook would need broad filesystem access.
8. The hook would mutate user work without explicit command intent.
9. The hook would make behavior harder to explain in a closeout.
10. The hook’s trigger condition is fuzzy or subjective.

**Candidate Hook Shape**

The hook should be bundled with the relevant plugin rather than installed as global agent behavior.

Recommended shape:

```text
plugin/
  .codex-plugin/
    plugin.json
  hooks/
    he-runtime-preflight/
      hook.json
      README.md
      run
      tests/
```

The hook should be opt-in at the plugin bundle level and inert unless its trigger condition is detected.

Suggested metadata:

```json
{
  "name": "he-runtime-preflight",
  "scope": "harness-engineering",
  "lifecycle": "preflight",
  "default": "disabled",
  "trigger": {
    "type": "runtime_condition",
    "requires_repeated_failure_evidence": true
  },
  "effects": {
    "mutates_canonical_sources": false,
    "mutates_user_files": false,
    "requires_network": false,
    "requires_write_access": false
  },
  "evidence": {
    "emits_structured_result": true,
    "records_trigger_condition": true,
    "records_action_taken": true
  }
}
```

**Allowed Hook Actions**

The hook may:

1. Detect known-bad runtime state.
2. Validate plugin projection presence.
3. Validate expected command wrappers are available.
4. Validate required runtime metadata exists.
5. Emit structured diagnostics.
6. Fail early with a specific remediation message.
7. Normalize ephemeral runtime state only when that state is owned by the plugin runtime and not by the user or canonical repo sources.

**Disallowed Hook Actions**

The hook must not:

1. Edit canonical skill files.
2. Edit AGENTS.md files.
3. Edit repo policy docs.
4. Rewrite task instructions.
5. Modify unrelated plugin state.
6. Install dependencies.
7. Fetch network resources.
8. Create commits.
9. Change git state.
10. Suppress validation failures.
11. Convert failing checks into warnings without explicit policy approval.

**Decision Gate**

A hook recommendation must pass this gate:

```text
Is the failure repeated?
If no, do not recommend.

Does the failure occur before normal skill instructions can reliably prevent it?
If no, fix the skill, docs, command, or validator instead.

Can an existing explicit command or wrapper solve it with equal or smaller scope?
If yes, use that path.

Can the hook trigger on a precise runtime condition?
If no, do not recommend.

Can the hook run without mutating canonical sources or user work?
If no, do not recommend unless explicitly approved as a separate high-risk change.

Can the hook emit structured evidence and fail closed?
If no, do not recommend.

Otherwise, recommend a bundled plugin hook as the smallest safe mechanism.
```

**Validation Plan**

The hook should ship with focused validation.

Required checks:

1. Trigger-negative test: hook does nothing when the failure condition is absent.
2. Trigger-positive test: hook detects the known repeated failure condition.
3. No-mutation test: hook does not edit canonical sources or user files.
4. Evidence test: hook emits structured output with trigger, action, and result.
5. Fail-closed test: hook exits with a clear diagnostic when it cannot safely proceed.
6. Rollback test: disabling the hook restores previous behavior.

Example robot-readable result:

```json
{
  "hook": "he-runtime-preflight",
  "status": "failed_closed",
  "triggered": true,
  "condition": "missing_runtime_projection",
  "action": "diagnostic_only",
  "mutated_files": [],
  "message": "Runtime projection is missing; rerun the projection sync command before continuing."
}
```

**Recommendation Language**

Use this wording when the evidence supports the hook:

```text
Recommend adding a bundled Harness Engineering plugin hook for this failure mode.

The recommendation is conditional on the attached runtime evidence: the failure has repeated, occurs before normal skill guidance can reliably prevent it, and cannot be addressed with a smaller docs, skill, wrapper, or validator change. The hook should be scoped to the detected runtime condition, run without mutating canonical sources or user work, emit structured evidence, and fail closed when it cannot safely recover.
```

Use this wording when the evidence does not support the hook:

```text
Do not recommend a bundled plugin hook yet.

The current evidence does not prove that a hook is the smallest safe mechanism. Prefer the narrower fix first: update the canonical instruction, command wrapper, validator, or workflow check that directly owns this failure. Reconsider a hook only if the same runtime failure repeats after that fix or if reproduction shows the failure occurs before ordinary workflow guidance can apply.
```

**Acceptance Criteria**

The bundled plugin hook spec is acceptable when:

1. It is explicitly conditional, not a default recommendation.
2. It defines repeated runtime failure evidence as a prerequisite.
3. It requires comparison against smaller mechanisms.
4. It limits the hook to plugin-owned runtime behavior.
5. It forbids canonical source mutation.
6. It requires structured evidence.
7. It requires fail-closed behavior.
8. It includes rollback expectations.
9. It provides recommendation and non-recommendation wording.
10. It can be validated with deterministic tests.

**Open Questions**

1. Which HE lifecycle event should own this hook: plugin load, preflight, command invocation, or closeout?
2. Where should repeated runtime failure evidence live so it is discoverable without bloating skill instructions?
3. Should hook enablement require an explicit plugin metadata flag, or should it be controlled by HE policy?
4. Should diagnostic-only hooks be allowed earlier than corrective hooks?
5. What command should closeout use to prove that hook behavior stayed within scope?
