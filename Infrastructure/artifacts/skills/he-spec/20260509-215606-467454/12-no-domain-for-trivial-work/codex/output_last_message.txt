Here’s a small, explicit spec for the cleanup.

**Spec: Trivial Skill Wording Cleanup**

**Goal**

Clean up wording in a single skill so the guidance is clearer, more direct, and less ambiguous, without changing the skill’s behavior, scope, domain model, tool routing, validation requirements, or runtime projections.

**Scope**

Update only the canonical skill source text for the targeted skill.

Allowed changes:

- Fix awkward phrasing.
- Remove redundant wording.
- Clarify existing instructions where the intended meaning is already clear.
- Normalize terminology to match repo language.
- Preserve the existing structure unless a tiny local rearrangement improves readability.
- Keep examples, commands, and references semantically unchanged.

Out of scope:

- No new skill capabilities.
- No routing changes.
- No package/runtime/projection edits.
- No changes to validation logic.
- No new tests unless existing repo policy requires proof for wording-only edits.
- No domain model changes.
- No command behavior changes.
- No broad refactor of neighboring docs.

**Domain Model Gates**

Domain model gates are explicitly **not applicable** for this change.

Reason:

This is a wording-only cleanup to an existing skill’s human-facing instructions. It does not introduce, rename, remove, or reinterpret any domain concepts, canonical entities, ownership boundaries, lifecycle states, sync behavior, handles, projections, validation semantics, or repo control-plane behavior.

Gate status:

- Domain terminology review: **N/A**
- Domain model update: **N/A**
- Ubiquitous language change: **N/A**
- Runtime projection/domain sync: **N/A**
- Migration/backfill concern: **N/A**
- Cross-skill domain contract change: **N/A**

**Acceptance Criteria**

The cleanup is complete when:

1. The target skill reads more clearly while preserving the same operational meaning.
2. No instruction expands or narrows the skill’s trigger conditions unless explicitly intended.
3. No canonical domain terms are added, removed, or redefined.
4. No runtime projection files are edited.
5. The diff is limited to the intended canonical source file, plus any required closeout metadata if the repo tooling generates it.
6. Validation evidence records that this was a wording-only change and that domain model gates were considered and marked **N/A**.

**Validation Plan**

Because this is a trivial wording cleanup:

1. Run the repo’s closeout/check command if available:

```bash
./bin/ask repo closeout --changed --json --robot
```

2. If the repo requires skill-specific proof for changed skills, run:

```bash
./bin/ask skills prove <handle> --json --robot
```

3. In the final evidence, explicitly state:

```text
Domain model gates: N/A, wording-only skill cleanup with no domain model, projection, routing, or behavior changes.
```

**Implementation Notes**

Before editing, follow the repo instruction to read:

```bash
UBIQUITOUS_LANGUAGE.md
```

Edit the canonical source only. Do not edit runtime projections. If the target skill has generated or synced copies elsewhere, leave them alone unless the repo’s documented workflow explicitly says to regenerate them through `./bin/ask`.

**Suggested Closeout Text**

```text
Implemented a trivial wording cleanup for <skill handle>. The change is limited to canonical skill wording and preserves existing behavior, routing, validation semantics, and domain terminology.

Domain model gates: N/A. This is a wording-only cleanup with no domain model changes, no projection changes, and no cross-skill contract changes.
```
