```md
## Plugin Hook Capability Check

Bundled plugin hooks are allowed into this spec only as a conditional design
candidate. They are not recommended for the first implementation slice unless
fresh runtime evidence proves that repeated lifecycle-timed failure cannot be
prevented by a smaller validator, eval, skill instruction, or release-runner
gate.

```yaml
plugin_hook_capability_check:
  verified_runtime_failure: "none_currently_proven_for_hook_recommendation"
  proposed_hook_event: "Stop"
  feature_gate_status: unknown
  fallback_path: "he-eval-report closure validation plus lifecycle release evals and routing-map validators"
  portability_check: partial
  side_effect_class: completion_gate
  lifecycle_authority: limited
  outcome: defer
```

Decision:

- Do not implement or recommend a bundled HE hook while the known failures can
  be repaired by SA-001 through SA-008.
- Reopen the hook candidate only if at least two independent runs show the same
  HE runtime failure after the fallback validator/eval path is present and
  passing in normal operation.
- If reopened, the smallest safe hook is a `Stop` handoff guard that blocks or
  warns only on a missing closure-proof artifact for the selected HE slice. It
  must not write `.harness` artifacts, mutate Linear, run network commands, or
  mark work complete.
- Hook declarations must stay plugin-portable: use `hooks/hooks.json` and
  `${PLUGIN_ROOT}` or `${PLUGIN_DATA}`, never Jamie-specific absolute paths.
- Closure proof must include both hook-enabled behavior and fallback behavior
  with `plugin_hooks` disabled or unavailable.
```

Add this behavior contract after the SA-004 section:

```md
### SA-009 Conditional Bundled Plugin Hook

Owner surface:

- `Plugins/harness-engineering/.codex-plugin/plugin.json`
- `Plugins/harness-engineering/hooks/hooks.json`
- `Plugins/harness-engineering/hooks/**`
- `Plugins/harness-engineering/references/plugin-hook-capability-contract.md`

Required implementation posture:

- Default action is defer. Do not add hook files, manifest declarations, or
  hook scripts during the Phase 1 repair unless fresh evidence proves the same
  runtime failure recurred after the validator/eval fallback path was available.
- The proof threshold is two matching runtime failures from independent runs
  where the agent missed a closure-proof or handoff requirement that only a
  lifecycle-timed hook could reasonably catch.
- If the threshold is met, spec the first hook as a `Stop` handoff guard with a
  visible message and explicit fallback command. `SessionStart` context primers
  and `PreToolUse` blockers remain out of scope unless separate repeated
  evidence proves they are smaller.
- The hook must be feature-gated and portable. It must tolerate
  `plugin_hooks` being disabled, unknown, or unavailable.
- The hook must not create `.harness` artifacts, mutate Linear, run broad
  validation, access credentials, call the network, or make completion claims.

Blocking proof:

- Before recommendation: a runtime-failure ledger cites the two matching
  failures, the selected slice, the fallback path that failed to prevent them,
  and why a validator/eval/skill wording change is insufficient.
- Before implementation closeout: hook-enabled proof shows the guard fires for
  the missing-proof case, and hook-disabled proof shows the fallback
  `he-eval-report` or release-eval path still blocks closure.
- Any hardcoded absolute path, hook-only closure authority, or missing fallback
  blocks the hook recommendation.
```
