# Trivial Skill Wording Cleanup

## Summary

Make a small wording-only cleanup to the target skill instructions. This change is limited to clarity, grammar, tone, and consistency. It must not change skill behavior, routing semantics, validation requirements, file ownership, projections, or runtime behavior.

## Goal

Improve the readability of the skill text while preserving the existing operational meaning exactly.

## Scope

In scope:

- Fix typos, awkward phrasing, duplicated words, and minor grammar issues.
- Tighten ambiguous sentences only where the intended meaning is already obvious from surrounding text.
- Normalize wording to match existing repo terminology.
- Preserve all command examples, paths, handles, policy references, and required phrases unless a typo is clearly present.
- Keep the diff intentionally small and reviewable.

Out of scope:

- Changing skill triggers, routing behavior, or activation criteria.
- Adding new workflow steps.
- Removing existing safeguards.
- Changing validation commands or closeout requirements.
- Moving content between canonical sources and runtime projections.
- Editing generated or projected runtime copies when a canonical source exists.
- Introducing new domain concepts, model terms, gates, lifecycle states, or governance rules.

## Domain Model Gates

Domain model gates are explicitly **not applicable** for this change.

Rationale:

- The change is wording-only.
- No domain model entities are added, removed, renamed, or reclassified.
- No lifecycle transitions, ownership boundaries, projections, sync rules, or policy gates are changed.
- No schema, command contract, or runtime behavior is affected.
- The implementation should not invoke domain-model review as a blocking gate.

## Implementation Notes

1. Read `UBIQUITOUS_LANGUAGE.md` before editing, per repo policy for skill changes.
2. Identify the canonical source for the target skill before editing.
3. Apply only wording-level edits.
4. Avoid expanding scope while touching nearby text.
5. Do not edit runtime projections unless the repo explicitly identifies them as canonical for the target file.
6. Keep the final diff small enough that a reviewer can verify semantic preservation line by line.

## Acceptance Criteria

- The wording is clearer or more consistent than before.
- The change does not alter the skill’s intended behavior.
- Domain model gates remain marked as not applicable.
- No generated/runtime projection is edited instead of a canonical source.
- No new validation, policy, or workflow requirement is introduced.
- Repo closeout reports no ownership or projection violations.

## Validation

```bash

./bin/ask repo closeout --changed --json --robot
```

If the target skill has a known handle and the wording change could affect discoverability or explanation text, also run:

```bash
./bin/ask skills explain <handle> --json --robot
./bin/ask skills prove <handle> --json --robot
```

## Non-Goals

- This is not a skill redesign.
- This is not a behavior change.
- This is not a routing change.
- This is not a domain model change.
- This is not an opportunity to restructure the skill or its surrounding docs.
