**Spec: Challenge-First HE Process Addition**

## Title

Add Challenge-First Gate for New Harness Engineering Processes

## Problem

Harness Engineering process additions risk becoming the default response to verified failures, even when the failure could be prevented with a narrower artifact: a reference contract, an eval, a validation fixture, or clearer acceptance criteria.

This creates unnecessary process surface area. New HE processes add maintenance burden, expand agent instruction load, and can obscure the actual invariant that failed. Before adding a new HE process, contributors need a required challenge step that asks whether the failure is better addressed by a smaller, testable contract or evaluation.

## Goal

Before a new HE process is added, require a documented scope challenge that determines whether the verified failure can be prevented with less scope.

The challenge must explicitly evaluate:

1. A reference contract.
2. An eval.
3. A validation/check update.
4. Existing process clarification.
5. A new HE process.

The new process should only proceed when the first four options are insufficient.

## Non-Goals

This change does not require every HE improvement to become an eval.

This change does not block process additions when the failure genuinely requires new recurring behavior.

This change does not replace existing closeout, proof, validation, or path ownership guidance.

This change does not define the full implementation of the new HE process itself. It defines the decision gate that must happen before adding one.

## Key Terms

**Verified failure**

A reproduced or evidence-backed failure mode with enough detail to identify what went wrong, what should have happened, and why the current system did not prevent it.

**Reference contract**

A canonical statement of expected behavior, interface, invariant, or evidence requirement that agents and tooling can cite or validate against.

**Eval**

A repeatable scenario, fixture, or benchmark that detects whether the failure has regressed.

**HE process**

A recurring operational workflow for Harness Engineering work, usually involving agent behavior, evidence gathering, validation sequence, review flow, or lifecycle governance.

## Decision Rule

A new HE process may be added only when the challenge finds that the verified failure cannot be reliably prevented by a reference contract, eval, validation update, or clarification to an existing process.

Use the narrowest sufficient artifact:

| Failure Shape | Preferred Remedy |
| --- | --- |
| Ambiguous invariant or expected behavior | Reference contract |
| Regression can be simulated or replayed | Eval |
| Existing command could catch it with stronger checks | Validation/check update |
| Agents skipped or misunderstood existing guidance | Clarify existing process |
| Failure requires new repeated coordination behavior | New HE process |

## Required Challenge

Before proposing a new HE process, the author must include a “Less-Scope Challenge” section.

The section must answer:

1. What is the verified failure?
2. What invariant was violated?
3. Could a reference contract prevent this?
4. Could an eval detect this?
5. Could an existing validation command or closeout check catch this?
6. Could an existing process be clarified instead?
7. Why is a new HE process still necessary?

The answer must include specific evidence, not just preference.

## Acceptance Criteria

A new HE process proposal is acceptable only if:

1. It identifies a concrete verified failure.
2. It names the failed invariant.
3. It evaluates reference contract, eval, validation, and existing process alternatives.
4. It explains why each smaller option is insufficient or only partially sufficient.
5. It defines what recurring behavior the new HE process adds.
6. It defines how the new process will be validated.
7. It identifies canonical source files that must change.
8. It avoids editing runtime projections directly.
9. It includes closeout evidence from the repo’s standard validation flow.

## Recommended Policy Text

Add this policy to the canonical HE/process authoring guidance:

```markdown
## Challenge New HE Processes First

Before adding a new Harness Engineering process, first challenge whether the verified failure can be prevented with a narrower artifact.

Prefer remedies in this order:

1. Reference contract.
2. Eval.
3. Validation/check update.
4. Clarification to an existing process.
5. New HE process.

A new HE process is appropriate only when the failure requires recurring behavior that cannot be captured by a contract, detected by an eval, enforced by validation, or addressed by tightening existing guidance.

Every new HE process proposal must include a Less-Scope Challenge section that evaluates these alternatives and explains why the new process is the narrowest sufficient fix.
```

## Example Less-Scope Challenge

```markdown
## Less-Scope Challenge

### Verified Failure

An agent completed an HE implementation but omitted session evidence in the closeout. The change passed local tests, but reviewers could not reconstruct why the implementation choices were made or whether prior failed approaches had been considered.

### Failed Invariant

HE changes must preserve enough evidence for future agents and reviewers to understand the decision path, validation path, and remaining risk.

### Reference Contract Assessment

Decision: partial

Rationale:

A reference contract could define the required evidence fields, but it would not ensure agents actually gather, attach, and validate that evidence during the lifecycle.

### Eval Assessment

Decision: partial

Rationale:

An eval could detect whether a final answer includes evidence, but the failure occurs across planning, implementation, and closeout. A narrow eval would be useful as regression coverage but would not fully define the workflow.

### Validation Assessment

Decision: partial

Rationale:

A closeout checker could catch missing fields after the fact. It would not guide agents through evidence collection while work is happening.

### Existing Process Assessment

Decision: no

Rationale:

Existing closeout guidance mentions evidence, but the failure shows agents need a dedicated sequence for collecting and preserving it during HE work, not just at the end.

### Process Justification

A new HE process is justified because the failure requires repeated lifecycle behavior: evidence discovery, evidence capture, validation linkage, and final closeout. A reference contract and eval should accompany the process, but neither is sufficient alone.
```

## Recommendation

I would not add the new HE process first.

I’d make the first deliverable a **reference contract plus eval assessment gate**. That gives the repo a small, durable pressure point: every future process proposal has to prove it really needs to exist. If the verified failure still cannot be prevented by that contract or eval, then the new HE process has a much cleaner justification and a sharper boundary.
