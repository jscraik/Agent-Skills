**Draft Spec**

**Title:** Bundled Plugin Hook for Harness Engineering Runtime Recovery

**Status:** Proposed, evidence-gated

**Owner:** Harness Engineering

**Decision Rule:** Do not recommend or implement a bundled plugin hook unless repeated runtime failure evidence shows that a hook is the smallest safe mechanism compared with docs, validation, command wrappers, skill routing, or runtime prompt changes.

**Problem**

Harness Engineering may encounter runtime failures that are hard to prevent through static docs or operator guidance alone. A bundled plugin hook could intercept a narrow class of failures and apply a deterministic recovery, guardrail, or diagnostic step.

However, hooks add hidden behavior to runtime execution. They can obscure cause and effect, increase debugging complexity, and create another policy surface. For HE, a hook should therefore be treated as a last-mile mechanism, justified only when the failure is:

1. Repeated across independent runs.
2. Runtime-specific rather than authoring-time or validation-time.
3. Not adequately addressed by existing repo commands, skill instructions, docs, projections, or validation.
4. Safer to handle with a small hook than with broader changes to the runtime, skill system, or operator workflows.

**Non-Goals**

This hook is not a general HE automation layer.

It should not:

- Replace `./bin/ask` workflows.
- Patch around unclear skill instructions.
- Compensate for stale docs or runtime projections.
- Add broad lifecycle orchestration.
- Make policy decisions that belong in canonical HE docs or validation.
- Mutate user work without explicit, auditable intent.
- Become the default place to fix workflow friction.

**Recommendation Gate**

The hook should only be recommended if all of the following are true:

| Gate | Requirement |
| --- | --- |
| Repetition | The same failure mode occurs in at least 3 separate runtime sessions or across at least 2 distinct agents/users. |
| Runtime locality | The failure occurs only or primarily during live runtime behavior, not during skill authoring, sync, install, validation, or docs discovery. |
| Minimality | A hook is smaller and safer than changing skill text, canonical docs, validation, repo wrappers, or runtime projections. |
| Determinism | The hook action can be deterministic, bounded, and easily tested. |
| Observability | The hook can emit clear evidence explaining when it fired, why it fired, and what it changed or advised. |
| Reversibility | The hook can be disabled without damaging existing HE workflows. |
| Ownership | Canonical source ownership is clear, and the hook does not edit runtime projections directly. |
| Safety | The hook cannot silently perform destructive actions, bypass repo policy, or override user/developer/system instructions. |

If any gate fails, the recommendation should be: **do not add a bundled plugin hook yet**.

**Evidence Required Before Recommendation**

A recommendation must include an evidence packet with:

```text
Failure name:
Failure class:
Observed sessions/runs:
Exact symptoms:
Exact commands or runtime actions involved:
Expected behavior:
Actual behavior:
Existing mitigations attempted:
Why docs/validation/wrappers/skill edits are insufficient:
Why a hook is smaller than alternatives:
Proposed hook trigger:
Proposed hook action:
Safety boundaries:
Disable/rollback path:
Validation plan:
```

A lightweight example:

```text
Failure name:
HE closeout loses required validation evidence

Observed sessions/runs:
- session A: closeout produced summary without pass/fail evidence
- session B: same pattern after skill route
- session C: same pattern after repo wrapper success

Existing mitigations attempted:
- Updated HE workflow doc
- Added validation checklist
- Confirmed agent still skipped evidence under runtime pressure

Why hook is smaller:
A post-closeout diagnostic hook can detect missing evidence in the final HE report and fail closed with a concise remediation prompt, without altering command behavior or broad skill routing.
```

**Hook Shape**

The bundled plugin hook should be narrow and declarative.

Suggested conceptual interface:

```json
{
  "name": "he-runtime-failure-guard",
  "scope": "harness-engineering",
  "trigger": {
    "event": "runtime_step_completed",
    "conditions": [
      "he_workflow_active",
      "known_failure_signature_detected"
    ]
  },
  "action": {
    "type": "diagnostic_or_guardrail",
    "mode": "fail_closed",
    "message": "Explain the detected failure and the smallest required correction.",
    "mutates_files": false,
    "runs_commands": false
  },
  "observability": {
    "emit_evidence": true,
    "include_trigger_reason": true,
    "include_disable_hint": true
  },
  "safety": {
    "never_override_higher_priority_instructions": true,
    "never_edit_runtime_projections": true,
    "never_perform_destructive_actions": true
  }
}
```

**Allowed Hook Behaviors**

The first version should only allow low-risk behaviors:

- Detect a known repeated failure signature.
- Emit a structured diagnostic.
- Block or warn before an unsafe continuation.
- Ask the agent to run an existing repo command.
- Attach evidence to HE closeout output.
- Route to an existing skill or `./bin/ask` command.
- Record that the failure signature occurred.

**Disallowed Hook Behaviors**

The hook should not:

- Modify files.
- Rewrite skills.
- Change AGENTS.md, policy docs, or runtime projections.
- Run package-manager commands.
- Run destructive git commands.
- Auto-commit.
- Auto-open or merge PRs.
- Suppress validation failures.
- Silently retry commands with changed arguments.
- Mask the original error.

**Preferred Hook Modes**

1. **Diagnostic-only mode**

   Best first step. The hook detects the failure and emits evidence.

   Example:

   ```text
   HE runtime guard triggered:
   known_failure_signature=missing_validation_evidence
   action=diagnostic_only
   next_step=run ./bin/ask repo closeout --changed --json --robot
   ```

2. **Fail-closed mode**

   Use only when continuing would likely produce invalid HE output.

   Example:

   ```text
   HE runtime guard blocked closeout because validation evidence is missing.
   Run the required closeout command and include pass/fail evidence.
   ```

3. **Advisory routing mode**

   The hook points the agent to a canonical workflow or skill, without doing the work itself.

   Example:

   ```text
   This appears to be HE session-evidence work. Use the harness-engineering skill and the repo closeout wrapper.
   ```

**Alternative Mechanisms to Try First**

Before recommending a hook, evaluate these in order:

1. **Canonical docs update**

   Use when the failure comes from ambiguity, stale terms, or missing guidance.

2. **Skill instruction update**

   Use when the agent knows the right context but chooses the wrong workflow.

3. **Validation/check improvement**

   Use when the failure can be caught by `./bin/ask` or another repo-owned check.

4. **Repo wrapper improvement**

   Use when the command contract should enforce the behavior.

5. **Runtime projection sync fix**

   Use when canonical guidance is correct but projections are stale.

6. **Bundled plugin hook**

   Use only when the failure happens during live runtime and cannot be reliably prevented earlier.

**Decision Matrix**

| Failure Type | Preferred Fix | Hook Fit |
| --- | --- | --- |
| Missing or unclear HE docs | Canonical docs | Poor |
| Agent skipped documented command | Skill/workflow instruction | Weak |
| Invalid output shape | Validation | Usually poor |
| Runtime repeatedly loses required evidence after valid commands | Diagnostic/fail-closed hook | Possible |
| Tooling bug in `./bin/ask` | Wrapper/tool fix | Poor |
| Projection stale relative to source | Sync/projection fix | Poor |
| Unsafe runtime continuation after recognizable failure | Fail-closed hook | Strong if repeated |
| Cross-cutting behavior needed by many plugins | Runtime/platform design | Poor for HE-specific hook |

**Acceptance Criteria**

A bundled plugin hook may be recommended only when the spec PR or planning doc includes:

- At least 3 concrete failure observations.
- A rejected-alternatives section.
- Proof that canonical-source edits alone were insufficient or inappropriate.
- A minimal hook trigger definition.
- A minimal hook action definition.
- An explicit no-mutation default.
- Clear observability output.
- A disable mechanism.
- Tests for trigger match and non-match cases.
- Tests proving the hook does not fire outside HE scope.
- Tests proving higher-priority instructions are not overridden.
- Closeout evidence using repo-standard commands.

**Test Plan**

Minimum validation:

```bash
./bin/ask repo doctor --json --robot
./bin/ask skills explain harness-engineering --json --robot
./bin/ask skills prove harness-engineering --json --robot
./bin/ask repo closeout --changed --json --robot
```

Hook-specific tests should cover:

- Does not fire when no known failure signature exists.
- Fires once for a known repeated failure signature.
- Emits trigger reason and recommended next step.
- Does not mutate files.
- Does not run commands unless the final accepted design explicitly allows command execution.
- Does not apply outside HE scope.
- Can be disabled.
- Produces machine-readable evidence for closeout.

**Recommended Spec Language**

I would phrase the recommendation like this:

```markdown
We should not add a bundled plugin hook for HE at this time unless the attached runtime evidence demonstrates a repeated failure mode that cannot be addressed safely through canonical docs, skill instructions, repo wrappers, validation, or projection sync.

If that evidence is present, the hook should be limited to diagnostic or fail-closed behavior for one named failure signature. The first version must not mutate files or run corrective commands. It should emit structured evidence explaining why it fired and what existing repo command or workflow the agent should use next.

The hook is acceptable only if it is the smallest safe mechanism.
```

**My Recommendation**

At this point, based only on the request and without live repo evidence, I would **not recommend building the hook yet**.
