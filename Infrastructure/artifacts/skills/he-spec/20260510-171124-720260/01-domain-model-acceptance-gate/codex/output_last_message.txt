# Workflow State Identity and Aggregate Invariants as Acceptance Criteria

## Summary

Workflow-state changes must treat entity identity and aggregate invariants as first-class acceptance criteria. A workflow is not accepted as correct merely because it advances between states or produces the expected visible output. It must also preserve the identity of every workflow entity across transitions and maintain the invariants of the aggregate that owns the workflow state.

This change makes workflow correctness testable at the domain boundary, not only at the UI, command, or persistence layer.

## Problem

Current workflow-state acceptance can be satisfied by checking state names, command success, emitted files, or terminal outcomes. That leaves a correctness gap: a workflow may appear to complete while silently mutating the wrong entity, losing identity continuity, creating duplicate aggregate members, or violating aggregate-level constraints.

Examples of failure modes this spec is intended to prevent:

- A workflow transition updates a newly-created entity instead of the existing canonical entity.
- A child record is moved between states without preserving its parent aggregate identity.
- A retry or resume path creates a duplicate workflow item instead of continuing the original item.
- A state transition succeeds while leaving the aggregate in an impossible mixed state.
- A projection, workpad, Linear issue, PR, or local state file refers to the same conceptual item using inconsistent identifiers.
- A test validates the final state label but does not prove that the same entity moved through the workflow.

These bugs are especially costly for agent-operated workflows because agents rely on durable identifiers, state files, and acceptance criteria to decide whether work is complete.

## Goal

For every workflow-state change, acceptance criteria must explicitly prove:

1. Entity identity is preserved across the transition.
2. The owning aggregate remains valid before and after the transition.
3. Resume, retry, and duplicate-input paths do not create conflicting identities.
4. External projections refer back to the canonical entity or aggregate identity.
5. Tests or validation evidence cover identity and invariant behavior, not only state labels.

## Non-Goals

This spec does not require a new workflow engine.

This spec does not require every existing workflow to be rewritten immediately.

This spec does not require every entity in the system to become an aggregate root.

This spec does not replace existing state-transition acceptance criteria. It adds identity and aggregate-invariant requirements to them.

## Definitions

### Entity Identity

Entity identity is the stable identifier that proves a workflow operation is acting on the same conceptual entity over time.

An entity identity may be represented by a database ID, issue key, handle, canonical path, UUID, repository object ID, or another stable domain identifier. The identifier must be durable enough to survive ordinary workflow transitions, retries, resumes, and projections.

### Aggregate

An aggregate is the consistency boundary that owns one or more workflow entities and enforces rules that must always remain true together.

Examples may include:

- A ticket and its workpad comments.
- A skill handle and its canonical source files.
- A repo workflow run and its validation artifacts.
- A PR and its review-thread resolution state.
- A generated projection and the canonical source it mirrors.

### Aggregate Invariant

An aggregate invariant is a rule that must remain true for the aggregate to be considered valid.

Examples:

- A workflow item has exactly one canonical owner.
- A child item cannot reference a parent that does not exist.
- A completed state cannot coexist with unresolved required blockers.
- A projection must reference the canonical source identity it was generated from.
- A retry must attach to the original workflow entity rather than create a competing one.
- A state transition must be monotonic unless the domain explicitly allows rollback.

## Required Acceptance Criteria

Any workflow-state change must include acceptance criteria for the following areas.

### 1. Canonical Identity

The spec, issue, or implementation plan must name the canonical identity field or identity surface for each workflow entity affected by the change.

Acceptance criteria:

- The workflow identifies the entity using the canonical identifier before applying the transition.
- The transition output includes or preserves the same canonical identifier.
- Any created child entity records the parent aggregate identity.
- No acceptance test relies only on display names, labels, titles, or inferred ordering when a stable identifier exists.

Example:

```text
Given workflow entity W has canonical id workflow_id=abc123
When W transitions from planned to in_progress
Then the persisted workflow entity still has workflow_id=abc123
And all transition artifacts reference workflow_id=abc123
```

### 2. Identity Continuity Across State Transitions

Every workflow transition must prove that the same entity moved from the prior state to the next state.

Acceptance criteria:

- The previous state and next state are associated with the same canonical entity identity.
- Transition logs, artifacts, or events contain enough identity evidence to trace the transition.
- Tests fail if the implementation creates a replacement entity without explicitly marking the original as superseded.
- State transition code does not infer the target entity from ambiguous inputs when a canonical identifier is available.

Example:

```text
Given issue JSC-299 has workflow entity id he-trust-defect-repair
When the workflow resumes after interruption
Then the resumed workflow attaches to he-trust-defect-repair
And no second active workflow entity is created for JSC-299
```

### 3. Aggregate Boundary

The change must identify the aggregate that owns the workflow state and the entities included in that consistency boundary.

Acceptance criteria:

- The owning aggregate is named in the spec or implementation notes.
- State changes are applied through the aggregate boundary or an equivalent canonical service.
- Child entities cannot be updated in a way that violates parent aggregate rules.
- External projections are treated as projections, not alternate aggregate owners.

Example:

```text
The Skill aggregate owns:
- skill handle
- canonical SKILL.md path
- examples/templates references
- generated runtime projection metadata

The runtime projection may reflect workflow state, but it must not become the source of truth for the skill identity.
```

### 4. Aggregate Invariants

Each workflow-state change must list the invariants that must hold before and after the transition.

Acceptance criteria:

- Required invariants are documented alongside the workflow-state change.
- Validation checks prove those invariants after transition.
- Invalid aggregate states fail fast with an actionable error.
- Tests cover at least one invariant violation path for non-trivial workflow changes.

Example invariant list:

```text
Invariant: A workflow item can have only one active owner.
Invariant: A completed workflow cannot have unresolved required blockers.
Invariant: A projection must reference an existing canonical source.
Invariant: A resumed workflow must reuse the original workflow identity.
```

### 5. Retry and Resume Behavior

Workflow-state changes must define what happens when the same operation is retried, resumed, or replayed.

Acceptance criteria:

- Re-running the transition with the same entity identity is idempotent or produces a documented domain error.
- Resume behavior reuses the existing workflow identity.
- Retry behavior does not create duplicate active entities.
- If a duplicate input is detected, the workflow reports the existing canonical identity.

Example:

```text
Given workflow entity W already exists for ticket JSC-299
When the start-workflow command is run again for JSC-299
Then the command returns W
And it does not create W2
And the response explains that the existing workflow entity was reused
```

### 6. Projection Consistency

Any state projected to files, comments, dashboards, Linear, GitHub, generated docs, or runtime mirrors must preserve identity references back to the canonical entity.

Acceptance criteria:

- Projection output includes the canonical entity or aggregate identity when practical.
- Projection refreshes update the existing projected record instead of creating an unrelated one.
- The projection can be traced back to its source entity.
- Tests or validation verify source-to-projection identity continuity.

Example:

```text
Given a workpad comment is the projection of workflow entity W
When W moves from in_progress to blocked
Then the workpad comment is updated for W
And no second workpad comment is created unless the workflow explicitly supports comment history
```

### 7. Conflict Detection

The workflow must detect identity or invariant conflicts before marking the transition successful.

Acceptance criteria:

- If two active entities claim the same aggregate role, the workflow blocks.
- If a child entity points at a missing or wrong parent, the workflow blocks.
- If projected state conflicts with canonical state, canonical state wins and the conflict is reported.
- Error messages include the conflicting identities and the invariant that failed.

Example error shape:

```json
{
  "ok": false,
  "error": "aggregate_invariant_failed",
  "aggregate_id": "JSC-299",
  "invariant": "single_active_workflow",
  "conflicting_entities": ["workflow-a", "workflow-b"]
}
```

### 8. Validation Evidence

Workflow-state changes must include validation evidence that specifically covers identity and aggregate invariants.

Acceptance criteria:

- At least one focused test proves identity continuity for the changed transition.
- At least one focused test or validator proves the key aggregate invariant.
- Closeout evidence records the exact validation command and result.
- Validation cannot be satisfied solely by a happy-path final-state assertion.

Acceptable validation forms:

- Unit test for transition behavior.
- Integration test for command/API workflow.
- Validator script that inspects persisted workflow state.
- Golden fixture proving projection identity references.
- Contract test for retry/resume behavior.

## Implementation Requirements

A workflow-state implementation satisfies this spec only when it does all of the following:

1. Names the canonical entity identity.
2. Names the owning aggregate.
3. Lists the invariants relevant to the changed transition.
4. Preserves identity across normal transition paths.
5. Preserves or explicitly reconciles identity across retry and resume paths.
6. Blocks or reports aggregate invariant violations.
7. Keeps external projections traceable to canonical identity.
8. Adds validation evidence for identity and invariant behavior.
9. Records exact validation commands and outcomes during closeout.

## Review Checklist

Reviewers must reject a workflow-state change when any of the following are true:

- The change describes only state labels and omits entity identity.
- The change has no named aggregate boundary.
- The change cannot explain what prevents duplicate active workflow entities.
- The change updates child state without proving the parent aggregate remains valid.
- The change treats a projection as the source of truth without an explicit migration decision.
- The tests only assert the final state and do not prove the same entity transitioned.
- Retry or resume behavior can create identity drift.
- Error handling hides the conflicting identity or failed invariant.

## Example: Minimum Acceptable Workflow-State Acceptance Criteria

```markdown
## Identity and Aggregate Acceptance Criteria

### Entity Identity

- Canonical entity: Harness execution workflow.
- Canonical identity field/surface: workflow_id stored in the workpad frontmatter.
- Identity must be preserved across start, resume, block, unblock, and complete transitions.

### Aggregate Boundary

- Owning aggregate: Linear issue execution aggregate.
- Included entities: Linear issue id, local workpad path, workflow_id, blocker records, validation evidence.
- External projections: Linear comments and generated closeout summary.

### Required Invariants

- One Linear issue may have only one active execution workflow.
- A completed workflow must have no unresolved required blockers.
- Every Linear comment projection must reference the workflow_id it summarizes.
- Resume must reuse the existing workflow_id for the issue.

### Retry and Resume

- Retry behavior: return the existing workflow when the same Linear issue already has an active workflow.
- Resume behavior: load by workflow_id first, then verify the Linear issue id matches.
- Duplicate input behavior: block with `single_active_workflow` if two active workflow ids exist for one issue.

### Validation Evidence

- Identity continuity validation: focused test for start -> resume -> complete preserving workflow_id.
- Aggregate invariant validation: focused test for duplicate active workflow detection.
- Projection consistency validation: fixture or integration test proving Linear comment update includes workflow_id.
```

## Migration Guidance

Existing workflow-state specs do not need to be rewritten all at once. Apply this requirement when:

- A workflow-state transition is added or changed.
- Retry, resume, projection, or closeout behavior changes.
- A workflow bug is caused by identity drift or duplicate entities.
- A workflow is promoted into agent-facing or automated operation.
- A reviewer identifies missing identity or aggregate-invariant acceptance criteria.

For older workflows, add the acceptance criteria opportunistically when touching the relevant workflow state.

## Open Questions

- Should identity and invariant checks become part of a shared validation helper?
- Should every workflow-state artifact include a standard `identity` block?
- Should projection outputs have a required `source_identity` field?
- Should duplicate active workflow detection be warning-only during migration or blocking immediately for new workflows?

## Decision

Workflow-state changes must include entity identity and aggregate invariants as acceptance criteria before they can be considered complete.

A final-state assertion is insufficient unless it also proves that the correct entity moved through the transition and that the owning aggregate remained valid.
