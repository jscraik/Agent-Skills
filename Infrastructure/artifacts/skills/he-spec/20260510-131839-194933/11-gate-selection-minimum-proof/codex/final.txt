**Acceptance Criteria: Gate Selection**

1. Standard work records minimum proof for every run.

   Given a standard work run completes,
   when the run summary, closeout, or robot output is inspected,
   then it includes the minimum proof required to understand what was checked.

   Minimum proof includes:
   - the selected gate set,
   - the reason each selected gate was required,
   - the command or check used for each selected gate,
   - the result of each selected gate,
   - the evidence location or relevant output summary,
   - the final pass, fail, or blocked status.

2. Standard work records skipped heavy gates.

   Given a heavy gate is available but not selected,
   when the run evidence is inspected,
   then the heavy gate is explicitly listed as skipped.

   Each skipped heavy gate includes:
   - the gate name,
   - the reason it was skipped,
   - the lighter proof or substitute check that was used, if any,
   - whether the skip was automatic, policy-driven, or manually chosen.

3. Gate selection distinguishes required, optional, and skipped checks.

   Given standard work evaluates a task,
   when gate selection output is produced,
   then each known gate is classified as one of:
   - `required`,
   - `optional`,
   - `skipped`,
   - `not_applicable`.

   The output must make clear which gates blocked completion and which did not.

4. Heavy gates are skipped only with an auditable rationale.

   Given a heavy gate is skipped,
   when the skip rationale is reviewed,
   then the rationale is specific to the current work and not a generic statement such as “not needed”.

   Acceptable rationales include:
   - no files in the gate’s ownership area changed,
   - the change is docs-only and the gate covers runtime behavior,
   - the package or subsystem required by the gate is unavailable,
   - a cheaper gate already covers the affected risk,
   - the task is blocked before the heavy gate can run.

5. Minimum proof survives robot-mode output.

   Given standard work is run with `--json --robot`,
   when the JSON output is parsed,
   then selected gates, skipped heavy gates, rationales, and evidence are present in machine-readable fields.

   The JSON must not require parsing prose to determine:
   - which gates ran,
   - which gates were skipped,
   - why each decision was made,
   - whether the work is pass, fail, or blocked.

6. Human-readable closeout includes the same gate decisions.

   Given a human-readable closeout is generated,
   when the closeout is read,
   then it summarizes the selected gates, skipped heavy gates, and minimum proof without losing information present in robot output.

7. Failed required gates prevent a passing closeout.

   Given a required gate fails,
   when standard work produces its final status,
   then the final status is `fail` or `blocked`, not `pass`.

   The output identifies:
   - the failed gate,
   - the failing command or check,
   - the relevant evidence,
   - the next recommended action.

8. Skipped heavy gates do not silently downgrade confidence.

   Given one or more heavy gates are skipped,
   when the final closeout is produced,
   then the closeout includes a residual-risk note if the skipped gate would have provided materially stronger assurance than the selected proof.

9. Gate selection is deterministic for the same inputs.

   Given the same changed files, task metadata, and available tooling,
   when gate selection is run repeatedly,
   then the same gates are selected or skipped with the same rationales.

10. Missing tooling is represented as blocked or skipped with evidence.

   Given a selected gate cannot run because required tooling, package roots, credentials, or services are unavailable,
   when standard work reports the result,
   then it records the gate as `blocked` or `skipped` with the exact missing prerequisite and the command or discovery step that proved it.

11. Gate selection respects path ownership boundaries.

   Given changes touch runtime projections or generated surfaces,
   when gate selection evaluates the work,
   then it identifies the canonical source path that should be validated or explains why no canonical source applies.

12. Docs-only and low-risk changes still record proof.

   Given a change does not require test, build, or integration gates,
   when standard work closes out,
   then it still records minimum proof such as:
   - files inspected,
   - policy or docs checks performed,
   - reason runtime gates were skipped,
   - final confidence or residual risk.

13. Heavy gate skip behavior is covered by tests.

   Given automated tests or fixtures exist for gate selection,
   when the test suite runs,
   then it verifies that skipped heavy gates appear in both human and robot outputs.

   Coverage includes at least:
   - a docs-only change,
   - a narrow skill-source change,
   - a broad runtime-affecting change,
   - a missing-tooling case.

14. Minimum proof fields are stable contract fields.

   Given downstream agents or automation consume gate output,
   when gate selection output changes,
   then the fields for selected gates, skipped gates, rationale, evidence, and final status remain backward-compatible or are versioned deliberately.

15. Closeout makes gate omissions visible.

   Given no heavy gates were selected,
   when the final closeout is read,
   then it is obvious whether heavy gates were:
   - not applicable,
   - skipped by policy,
   - unavailable,
   - replaced by lighter proof.
