Here’s the spec I’d propose.

**Bundled Plugin Hook Spec**

**Purpose**

Add a narrowly scoped bundled plugin hook for Harness Engineering only when repeated runtime failures demonstrate that normal skill instructions, repo docs, validation commands, or agent workflow guidance are insufficient.

The hook is not a convenience mechanism. It is an escape hatch for a proven runtime reliability gap.

**Recommendation Rule**

Recommend the hook only if all of these are true:

1. A runtime failure has occurred repeatedly.
2. The failure has been observed in real HE execution, not only predicted.
3. The repeated failures share the same underlying cause.
4. Existing mechanisms have already been tried or are clearly inadequate:
   - skill instructions
   - AGENTS.md guidance
   - operator docs
   - validation wrappers
   - repo command wrappers such as `./bin/ask`
   - runtime projection updates
5. The hook is the smallest safe intervention.
6. The hook can be bounded, observable, and reversible.
7. The hook does not silently mutate user work or bypass repo policy.

If any condition is missing, the recommendation should be: **do not add a bundled plugin hook yet**.

**Failure Evidence Required**

Before recommending the hook, capture evidence in a compact failure record:

```markdown
## Runtime Failure Evidence

Failure class:
Observed in:
Occurrences:
Common trigger:
Expected behavior:
Actual behavior:
Existing mitigations tried:
Why existing mechanisms failed:
Smallest safe mechanism:
Residual risk:
Rollback path:
```

A hook recommendation should require at least two independent occurrences, unless the single occurrence caused high-impact corruption, security exposure, or irreversible workflow failure.

**Eligible Failure Classes**

A bundled plugin hook may be appropriate for HE when the repeated runtime failure is one of these:

1. **Preflight omission**
   Agents repeatedly start HE work without required repo or policy context, causing invalid edits or invalid validation paths.

2. **Wrong source edited**
   Agents repeatedly edit runtime projections instead of canonical sources despite path ownership guidance.

3. **Validation bypass**
   Agents repeatedly finish HE work without required repo validation evidence when validation is available.

4. **Unsafe lifecycle transition**
   Agents repeatedly publish, sync, close out, or mark work complete without satisfying explicit HE lifecycle requirements.

5. **Known runtime mismatch**
   The runtime environment repeatedly differs from the documented workflow in a way that cannot be corrected by docs alone.

**Non-Eligible Cases**

Do not recommend a hook for:

1. One-off failures.
2. Style preference enforcement.
3. Better reminders that could live in AGENTS.md or skill docs.
4. Gaps caused by unclear product requirements.
5. Failures that can be handled by improving `./bin/ask` output.
6. Failures requiring judgment that a deterministic hook cannot safely encode.
7. Anything that would hide errors instead of surfacing them.

**Hook Shape**

The hook should be as small as possible and should prefer **detection and interruption** over automatic mutation.

Recommended order of hook behavior:

1. Detect the risky condition.
2. Emit a clear machine-readable warning or failure.
3. Point to the canonical command or doc.
4. Require the agent to re-run the correct workflow.
5. Avoid editing files automatically unless the operation is fully deterministic and reversible.

Example behavior:

```text
HE hook detected edits under runtime projection paths.

Canonical sources must be edited instead.
See Docs/agents/14-path-ownership-boundaries.md.

Action required:
Run ./bin/ask skills explain <handle> --json --robot
then update the canonical source path reported by the tool.
```

**Hook Types**

Prefer these hook types, in order:

1. **Preflight hook**
   Runs before HE task execution or before a risky command path.

2. **Validation hook**
   Runs during closeout or proof collection.

3. **Guard hook**
   Blocks a known unsafe action with a precise explanation.

4. **Repair hook**
   Only if the repair is deterministic, minimal, and cannot destroy user work.

Avoid background hooks, broad interceptors, and hooks that infer intent from ambiguous file names.

**Safety Constraints**

The hook must:

1. Be scoped to Harness Engineering workflows.
2. Be opt-in or bundled only with the relevant HE plugin/runtime.
3. Never revert user changes.
4. Never run destructive commands.
5. Never bypass `./bin/ask` when repo policy says to use it.
6. Produce structured output suitable for `--json --robot` consumers.
7. Include an explicit bypass path only if policy allows one.
8. Fail closed only for proven high-risk operations.
9. Fail open with a warning for lower-risk uncertainty.

**Decision Matrix**

Use this matrix before recommending the hook:

| Question | If yes | If no |
|---|---|---|
| Has the same failure repeated? | Continue | Do not recommend hook |
| Is the failure runtime-specific? | Continue | Fix docs/spec/instructions |
| Did normal guidance fail? | Continue | Improve guidance first |
| Is the hook smaller than changing the workflow? | Continue | Change workflow/tooling instead |
| Can it be safely detected? | Continue | Do not hook |
| Can it be reversed or bypassed safely? | Continue | Do not hook |
| Does it preserve user work? | Recommend | Do not hook |

**Recommendation Language**

When evidence is insufficient:

```markdown
I do not recommend a bundled plugin hook yet.

The failure has not been shown to repeat under HE runtime conditions, and the smaller mechanism is still to improve the existing instruction or validation path. Revisit this only after repeated runtime evidence shows the same failure escaping normal guidance.
```

When evidence is sufficient:

```markdown
I recommend a bundled HE plugin hook for this failure class.

The same runtime failure has occurred repeatedly, existing guidance and validation paths did not prevent it, and a narrow detection hook is the smallest safe mechanism. The hook should detect the unsafe condition, stop the workflow before mutation or closeout, emit structured guidance, and point the agent back to the canonical HE command path.
```

**Acceptance Criteria**

A bundled HE plugin hook is acceptable only when:

1. The failure record includes repeated runtime evidence.
2. The hook has a single named failure class.
3. The hook’s trigger condition is deterministic.
4. The hook’s output includes the exact corrective command or doc path.
5. The hook has tests for:
   - positive detection
   - safe non-detection
   - ambiguous case behavior
   - structured output shape
6. The hook has a documented rollback path.
7. The hook is referenced from the HE operator docs or plugin docs.
8. The closeout evidence shows the hook does not interfere with unrelated workflows.

**Suggested Spec Title**

`Conditional Bundled Hook Policy for Harness Engineering Runtime Failures`

**Short Version**

The policy should say:

> Bundled plugin hooks for Harness Engineering are allowed only as a last-mile runtime guard. They should be recommended only after repeated observed failures prove that instructions, docs, validation wrappers, or command improvements are insufficient, and only when the hook is the smallest safe, observable, reversible mechanism.
