**Validation Gates**

Gate 0: Scope and ownership confirmation
Pass criteria:
- Identify the exact defect or behavior being repaired.
- Identify the canonical source files that own the behavior.
- Confirm we are editing canonical sources, not runtime projections or generated mirrors.
- Confirm no unrelated dirty worktree changes are touched.

Evidence to collect:
- `git status --short`
- Exact paths in scope
- Any relevant ownership docs, especially `UBIQUITOUS_LANGUAGE.md` and `Docs/agents/14-path-ownership-boundaries.md` if skills, projections, or agent-facing docs are involved.

Gate 1: Instruction and policy alignment
Pass criteria:
- Root `AGENTS.md` has been applied.
- Any nearer scoped `AGENTS.md` has been applied.
- For technical changes under `codex/`, `codex/instructions/CODESTYLE.md` or the applicable `instructions/CODESTYLE.md` front door has been read before implementation.
- If the change touches validation/preflight/workflow entrypoints, `$validation-contract-check` applies.
- If the change touches config, hooks, agents, installers, symlinks, or projection docs, `$config-drift-guard` applies.
- If the change touches MCP startup, Local Memory, `mise`, login shell drift, or `codex mcp list`, `$mcp-startup-triage` applies.
- If the change touches required CI check names, `$ci-check-name-parity` applies.

Evidence to collect:
- Exact instruction files read
- Exact triggered skill or reason no mandatory skill applies

Gate 2: Baseline health before edits
Pass criteria:
- Existing repo health is understood before changing anything.
- Known pre-existing failures are recorded separately from implementation regressions.
- Since this session says `bash scripts/codex-preflight.sh --mode optional` already passed, that can count as baseline preflight unless the implementation scope changes materially.

Evidence to collect:
- Current `git status --short`
- Existing pass/fail result for `bash scripts/codex-preflight.sh --mode optional`
- Any known local blockers called out before edits

Gate 3: Focused implementation validation
Pass criteria:

- For skill changes, prefer the repo wrapper flow, for example:
  - `./bin/ask skills explain <handle> --json --robot`
  - `./bin/ask skills prove <handle> --json --robot`

  - `./bin/ask repo doctor --json --robot`

  - `python3 scripts/validate-codex-config.py`
  - `bash scripts/validate-codex-hooks.sh`
  - `bash scripts/audit-codex-symlinks.sh`

Evidence to collect:
- Exact command
- Exit status
- Important output lines
- Whether failure is new, pre-existing, or environmental

Gate 4: Contract and regression validation
Pass criteria:
- The changed behavior is validated through the public/agent-facing command path, not only by inspecting files.
- JSON/robot output remains parseable where required.
- No command contracts, handles, required fields, or projection assumptions drift unintentionally.
- Documentation and implementation agree.

Evidence to collect:
- One direct command demonstrating the repaired behavior
- One command proving the broader contract still works
- Any generated output or artifact path, if applicable

Gate 5: Closeout validation
Pass criteria:
- Run closeout over changed files:
  - `./bin/ask repo closeout --changed --json --robot`
- Confirm only intended files changed.
- Confirm uncommitted pre-existing work remains untouched.
- Record any skipped validation with exact reason.

Evidence to collect:
- `git diff --stat`
- `git diff --name-only`
- `./bin/ask repo closeout --changed --json --robot`
- Final pass/fail/blocked summary

**Rollback Conditions**

Rollback immediately, or stop and ask before continuing, if any of these happen:

1. Ownership boundary violation
Rollback condition:
- The fix requires editing runtime projections, generated files, synced mirrors, or home-directory outputs instead of canonical sources.

Action:
- Stop implementation.
- Re-identify canonical source.
- Do not preserve projection-only edits.

2. Instruction conflict
Rollback condition:
- Root guidance, scoped `AGENTS.md`, codestyle guidance, skill guidance, or workflow docs disagree in a way that affects the implementation.

Action:
- Stop.
- Report the contradiction with exact file paths.
- Resolve the policy conflict before code changes continue.

3. Validation contract drift
Rollback condition:
- The implementation changes validation/preflight behavior without updating the corresponding docs, wrappers, or contract checks.
- A command’s JSON/robot output shape changes unintentionally.
- A previously documented command no longer exists or changes semantics.

Action:
- Roll back the incompatible part of the change or update the canonical contract intentionally.
- Re-run the focused contract validation.

4. New baseline failure
Rollback condition:
- A validation command that passed before edits fails after edits, and the failure is plausibly caused by the implementation.

Action:
- Revert only our own changes related to that failure.
- Preserve unrelated user work.
- Re-run the failing command to confirm recovery.

5. Dirty worktree collision
Rollback condition:
- The fix requires overwriting, reformatting, or restructuring files with unrelated existing user changes.

Action:
- Stop and isolate the intended hunk.
- If clean isolation is not possible, ask for direction.
- Do not run broad formatters over mixed-change files.

6. Skill/projection drift
Rollback condition:
- A skill handle, route, generated projection, or sync path changes in a way that makes discovery, install, prove, or explain commands disagree.

Action:
- Restore handle/route consistency at the canonical source.
- Re-run the relevant `./bin/ask skills ... --json --robot` checks.

7. External state mismatch
Rollback condition:
- Local artifacts imply one state, but Linear/GitHub/CI or repo command output says another.
- This especially matters if implementation is tied to a ticket, PR, required check, or live tracker.

Action:
- Stop treating local files as sufficient.
- Refresh live state before continuing.

8. Destructive shortcut required
Rollback condition:
- Progress appears to require `git reset --hard`, deleting broad directories, force-pushing, rewriting unrelated history, or otherwise discarding work.

Action:
- Do not proceed without explicit approval.
- Prefer surgical reversal of only our own changes.

9. Incomplete verification
Rollback condition:
- The code “looks right” but cannot be validated through the repo’s public wrapper or focused command path.

Action:
- Mark as blocked rather than done.
- Keep implementation only if the blocker is clearly environmental and the exact blocker is recorded.

10. Scope creep
Rollback condition:
- The implementation starts expanding into unrelated cleanup, broad refactors, stale doc rewrites, or opportunistic improvements.

Action:
- Cut back to the defect repair.
- Leave follow-up candidates as notes, not bundled changes.

**Minimum Acceptance Bar**

For this repo, I would not consider the implementation ready unless we can show:

- Intended files only in `git diff --name-only`.
- The relevant smallest command passes.
- `./bin/ask repo closeout --changed --json --robot` passes or has a clearly classified pre-existing/environmental blocker.
- Any mandatory skill lane triggered by the touched files has been followed.
- Any rollback condition encountered has either been resolved or explicitly reported as a blocker.
