I would **not** switch the hook pack to `features.hooks` as the only emitted key yet.

**Why**
- The current official Codex docs still list `features.codex_hooks` as the supported stable feature flag in the config reference and config basics.
- The hooks docs and plugin packaging docs still describe lifecycle hooks as `hooks.json` or inline `[hooks]`, with `codex_hooks` as the enabling feature flag.
- I did not find any official docs evidence that `features.hooks` is a published replacement contract yet.

**What I’d recommend instead**
- Keep `features.codex_hooks` as the canonical key for now.
- If you want to prepare for a future rename, emit `features.hooks` only as an additive compatibility path after runtime capability detection, not as a hard replacement.
- Do not drop `codex_hooks` until you have a confirmed minimum runtime version that supports the new key.
- Add a regression test that proves older runtimes still receive `codex_hooks`.

**Net**
- A hard move to `features.hooks` would be a compatibility risk.
- A dual-write migration is the safer path if you really need to hedge for newer runtimes.
