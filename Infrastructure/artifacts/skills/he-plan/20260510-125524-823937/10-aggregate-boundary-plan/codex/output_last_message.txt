**Goal**

Make the Account model the explicit lifecycle owner for account creation, activation, suspension, closure, and any domain invariants that must hold across account-owned entities. Implementation order should follow ownership:

1. Define the aggregate and lifecycle language.
2. Move invariants to the Account boundary.
3. Rewire write paths through Account-owned operations.

**First Principles**

The Account aggregate should own state transitions that answer questions like:

- Can this account be created?
- Can it be activated?
- Can it be suspended?
- Can it be closed?
- Which child entities are account-owned versus merely account-associated?
- Which operations require the Account to be active, trusted, billable, verified, or not closed?
- Which lifecycle events are authoritative domain facts rather than incidental database updates?

The implementation order should therefore start at the domain boundary, then move outward. Anything that only observes Account state should be updated after the aggregate behavior is settled. Anything that mutates Account-owned lifecycle state should be brought under the aggregate before surrounding callers are cleaned up.

**Phase 1: Define The Account Aggregate Boundary**

Start with the Account aggregate because every later step depends on who owns which invariants.

Clarify and document the boundary in the canonical domain source, not a projection.

The Account aggregate should explicitly own:

- Account identity.
- Account lifecycle state.
- Valid lifecycle transitions.
- Account-level invariants.
- Account-owned child entities, if any.
- Account domain events.
- Policies that are inseparable from lifecycle state.

The Account aggregate should not necessarily own:

- Read-only projections.
- External provider state, except as references or verified facts.
- UI display preferences unless they are account lifecycle constraints.
- Cross-aggregate orchestration that belongs to an application service or process manager.
- Derived search, analytics, or sync data.

Example lifecycle vocabulary to settle:

```text
Pending
Active
Suspended
Closed
```

Or, if the domain already has richer language:

```text
Provisioned
Verified
Enabled
Restricted
Deactivated
Archived
```

Do not invent new terms if `UBIQUITOUS_LANGUAGE.md` already defines them.

Deliverable:

- A small canonical note or domain source update that says: “Account owns lifecycle state and lifecycle transitions for X, Y, Z.”
- A list of operations that must pass through Account.

**Phase 3: Move Lifecycle Rules Into Account**

Implement lifecycle transition methods before changing callers.

This is the core ordering rule: first make the aggregate capable of protecting itself, then route mutation paths through it.

Candidate aggregate methods:

```text
Account.create(...)
Account.activate(...)
Account.suspend(reason)
Account.reinstate(...)
Account.close(reason)
Account.rename(...)
Account.attachOwnedResource(...)
Account.detachOwnedResource(...)
```

Each method should enforce its own transition validity.

Examples of invariants:

```text
A closed account cannot be reactivated.
A suspended account cannot perform active-only operations.
An account cannot be closed while required owned resources are still active.
An account cannot be activated until required identity or setup facts exist.
Only Account can emit AccountActivated, AccountSuspended, or AccountClosed.
```

Events should be emitted from the aggregate if the codebase uses domain events:

```text
AccountCreated
AccountActivated
AccountSuspended
AccountReinstated
AccountClosed
```

Do this before touching services, controllers, workers, or projections.

Deliverable:

- Account lifecycle methods.
- Focused unit tests for valid and invalid transitions.
- Domain events, if that is an established local pattern.

**Phase 4: Route Existing Mutations Through Account**

Only after the aggregate protects its lifecycle should callers be updated.

Implementation order inside this phase:

1. Application services.
2. Command handlers or use cases.
3. Background jobs.
4. API handlers/controllers.
5. Admin or CLI tooling.
6. Tests around public behavior.

Each caller should stop manually assigning lifecycle fields and instead call the aggregate operation.

Before:

```text
account.status = "suspended"
account.suspended_at = now
```

After:

```text
account.suspend(reason, actor, now)
```

The exact shape should follow the repo’s language and patterns, but the key is that lifecycle mutation becomes a domain operation.

Deliverable:

- No direct lifecycle state mutation outside the aggregate, except persistence/hydration code.
- Existing workflows still pass.
- New tests cover at least one caller per lifecycle transition.

**Phase 5: Separate Lifecycle Ownership From Process Ownership**

This is the subtle part.

The Account aggregate owns whether a transition is valid and what domain facts result. It should not necessarily own every side effect caused by that transition.

For example:

Account owns:

```text
Suspended -> Active is allowed.
AccountReinstated event is emitted.
Account state changes to Active.
```

Application/process layer owns:

```text
Send email.
Update billing provider.
Rebuild search index.
Notify integrations.
Start sync job.
```

This separation prevents the aggregate from becoming a service locator while still making it the source of truth for lifecycle.

Deliverable:

- Side effects subscribe to Account events or are coordinated after aggregate commit.
- Account remains free of infrastructure dependencies.
- Process code no longer decides lifecycle validity.

**Risk Checks**

Watch for these failure modes:

- Lifecycle state is updated directly in persistence code outside aggregate hydration.
- “Account status” appears in multiple enums or string unions with diverging meanings.
- A child entity is treated as account-owned in one workflow and independent in another.
- Side effects are moved into Account and make the aggregate depend on infrastructure.
- Projections are edited directly instead of regenerated.
- Tests assert implementation details instead of lifecycle behavior.
- Account closure is treated as deletion when the domain needs historical ownership.
