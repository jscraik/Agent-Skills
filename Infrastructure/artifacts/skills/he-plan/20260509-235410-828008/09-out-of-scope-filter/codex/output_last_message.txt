So I can’t safely classify live files or current diffs from the tree. Based on your phrasing, the clean separation I’d use is:

**Must Implement Now**

Put work here only if it is required for the current change to be correct, reviewable, and shippable.

That includes:

- Fixes needed to satisfy the stated user-facing behavior.
- Validation required to prove the change works.
- Updates to canonical docs or skill sources when the implementation changes agent behavior.
- Removal of contradictions that would cause agents to do the wrong thing immediately.
- Small supporting refactors only when they directly reduce risk in the current change.
- Tests or proofs that cover the behavior being changed.
- Any compatibility or ownership-boundary update required by existing repo policy.

A good test: if this item is not done, would the current implementation be incomplete, misleading, unsafe, or likely to fail review? If yes, it belongs here.

**Follow-Up Work**

Put work here only if it is valuable but not required for correctness of the current change.

That includes:

- Nice-to-have cleanup.
- Broader refactors discovered along the way.
- Improvements to adjacent skills, docs, commands, or naming that are not needed for this change.
- Extra test coverage outside the touched behavior.
- UX polish or wording refinements that do not affect agent execution.
- Future automation or tooling improvements.
- Deprecation cleanup that can be scheduled separately.
- Open questions that need product or maintainer judgment.

A good test: if this item is skipped, does the current change still behave correctly and remain understandable? If yes, it is follow-up.

**What Should Not Become Noise**

I’d exclude these from both lists unless they are tied to a concrete failure:

- Vague “improve docs” items.
- “Consider refactoring” without a target file and reason.
- Hypothetical edge cases with no current path to failure.
- Preferences that are not backed by repo policy or observed behavior.
- Duplicates of existing guidance.
- Large “while we’re here” changes.
- Aspirational architecture notes without an owner or trigger.
- TODOs that do not say what decision or evidence is needed.

**Suggested Format**

```md
## Required for This Change

- [ ] Implement <specific behavior> in <canonical path>.
- [ ] Update <specific doc/source> because <agent-facing behavior changed>.
- [ ] Validate with `<exact command>`.
- [ ] Capture evidence from `<exact command or proof>`.

## Follow-Up, Not in Scope

- [ ] <Specific future improvement>. Trigger: <when this becomes worth doing>.
- [ ] <Specific cleanup>. Owner/context: <optional>.
- [ ] <Specific question>. Needs: <decision/evidence>.

## Dropped as Noise

- <Item>, because <why it is not actionable or not relevant now>.
```

**Decision Rule**

Use this boundary:

> Current work should include only what is necessary to make the intended behavior true, policy-compliant, and proven. Everything else needs a concrete trigger, owner, or evidence requirement before it earns space as follow-up.
