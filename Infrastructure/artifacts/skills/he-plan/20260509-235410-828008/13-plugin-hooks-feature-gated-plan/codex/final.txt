**Goal**

Add bundled plugin hooks as an optional, feature-gated behavior. The system should work in three states:

1. Hooks feature disabled globally: bundled plugins still validate and operate using existing behavior.
2. Hooks feature enabled, plugin has hooks: hooks are discovered, validated, and included in runtime/bundle output.
3. Hooks feature enabled, plugin has no hooks or invalid hooks: absence is accepted, invalid configured hooks fail with clear validation.

**Core Design**

Add `plugin_hooks` as an optional capability on bundled plugins, not as a required part of the plugin contract.

The important shape is:

```json
{
  "plugin_hooks": {
    "enabled": true,
    "hooks": [
      {
        "name": "pre_install",
        "command": "...",
        "timeout_seconds": 30
      }
    ]
  }
}
```

But I’d avoid committing to this exact schema until checking the current plugin manifest model. The repo likely already has canonical plugin metadata under a `.codex-plugin/plugin.json` style boundary, so the real move is to extend the existing manifest schema instead of adding a parallel config surface.

**Feature Gate**

Introduce a single feature flag around hook behavior, ideally using the repo’s existing feature-gate/config pattern.

Possible names:

```text
plugin_hooks
enable_plugin_hooks
bundled_plugin_hooks
```

I’d prefer `plugin_hooks` if the repo already uses terse capability keys, or `enable_plugin_hooks` if flags are Boolean and imperative elsewhere.

Behavior matrix:

| Feature flag | Manifest has `plugin_hooks` | Result |
|---|---:|---|
| disabled | absent | pass |
| disabled | present | pass with hooks ignored, optionally warn |
| enabled | absent | pass |
| enabled | present and valid | pass |
| enabled | present and invalid | fail validation |

The fallback rule matters: validation must not require hooks unless hooks are both enabled and declared.

**Implementation Plan**

1. **Find plugin manifest ownership**

   Identify where bundled plugin metadata is defined and validated. The files to inspect are likely around:

   ```text
   .codex-plugin/plugin.json
   .agents/plugins/marketplace.json
   Infrastructure/
   Docs/agents/
   ```

   The deliverable from this step is a short note:

   ```text
   Canonical schema:
   Runtime projection:
   Validator:
   Bundle/sync path:
   Tests:
   ```

2. **Extend canonical plugin schema**

   Add an optional `plugin_hooks` field to the canonical plugin manifest schema.

   Requirements:

   ```text
   plugin_hooks is optional.
   If omitted, existing plugins remain valid.
   If present while feature gate is disabled, schema-level validation should still accept it if the field is syntactically valid.
   Hook execution/discovery validation is gated separately.
   ```

   Suggested minimal shape:

   ```json
   {
     "plugin_hooks": {
       "hooks": [
         {
           "name": "post_install",
           "command": "scripts/post-install.sh",
           "timeout_seconds": 30
         }
       ]
     }
   }
   ```

   But if the repo has a standard typed command/action model, use that instead of inventing command fields.

3. **Add feature-gated validation path**

   Split validation into two layers:

   ```text
   Structural validation:
   Always validates shape when plugin_hooks is present.

   Behavioral validation:
   Only validates hook references/executability when plugin_hooks feature is enabled.
   ```

   This prevents a disabled optional feature from breaking bundled plugin validation.

   Pseudocode:

   ```ts
   validatePluginManifest(manifest, context) {
     validateBasePlugin(manifest)

     if (manifest.plugin_hooks) {
       validatePluginHooksShape(manifest.plugin_hooks)
     }

     if (context.features.plugin_hooks && manifest.plugin_hooks) {
       validatePluginHooksBehavior(manifest.plugin_hooks, context)
     }
   }
   ```

   If the codebase is Ruby/Python instead of TypeScript, preserve the same split.

4. **Add fallback validation when hooks are disabled**

   The fallback should prove that the plugin remains valid without considering hooks.

   Add a validation mode equivalent to:

   ```text
   validate bundled plugin with hooks enabled
   validate bundled plugin with hooks disabled
   ```

   If hooks are disabled, validation should report something like:

   ```json
   {
     "plugin_hooks": {
       "status": "skipped",
       "reason": "feature_disabled"
     }
   }
   ```

   That gives agents and CI a stable machine-readable result without treating skipped hooks as success-by-accident.

5. **Update bundling/projection logic**

   If bundled plugins are copied, packed, projected, indexed, or emitted into marketplace metadata, preserve `plugin_hooks` only where appropriate.

   Recommended behavior:

   ```text
   Canonical plugin manifest: may include plugin_hooks.
   Runtime projection with hooks enabled: include plugin_hooks.
   Runtime projection with hooks disabled: either omit plugin_hooks or include with skipped metadata, depending on existing projection conventions.
   Marketplace/index file: include only discovery metadata needed by the runtime.
   ```

   I’d lean toward preserving the field in static metadata and making the runtime decide whether to use it. That avoids losing information in projections and keeps feature-gating centralized.

6. **Add tests for both modes**

   Minimum test matrix:

   ```text
   Existing plugin without plugin_hooks validates with feature disabled.
   Existing plugin without plugin_hooks validates with feature enabled.
   Plugin with valid plugin_hooks validates with feature enabled.
   Plugin with valid plugin_hooks validates with feature disabled and reports skipped/ignored.
   Plugin with invalid plugin_hooks fails structural validation even if feature disabled.
   Plugin with structurally valid but behaviorally invalid hooks fails only when feature enabled.
   Plugin with structurally valid but behaviorally invalid hooks passes fallback validation when feature disabled.
   ```

   The distinction between structurally invalid and behaviorally invalid is key.

   Examples:

   ```text
   Structurally invalid:
   plugin_hooks is a string, hook name missing, timeout is negative.

   Behaviorally invalid:
   hook command references a missing file, hook target is not executable, unsupported hook lifecycle name.
   ```

7. **Update docs**

   Add docs in the canonical agent-facing location, likely under `Docs/agents/`.

   The docs should state:

   ```text
   plugin_hooks is optional.
   Hooks are feature gated.
   Disabled hooks must not block plugin validation.
   Validators should run fallback mode when hooks may be unavailable.
   Runtime projections are generated from canonical sources.
   ```

   Also update any operator docs that mention bundled plugin validation.

8. **Add closeout validation**

   Per AGENTS.md, use root wrappers and robot JSON:

   ```bash
   ./bin/ask repo doctor --json --robot
   ./bin/ask repo closeout --changed --json --robot
   ```

   If there is a plugin-specific validator, run it too. Likely candidates to discover:

   ```bash
   ./bin/ask skills explain plugin-factory --json --robot
   ./bin/ask skills prove <affected-handle> --json --robot
   rg "plugin.*validate|validate.*plugin|bundle.*plugin" .
   ```

**Acceptance Criteria**

The work is done when:

```text
plugin_hooks can appear in bundled plugin metadata without breaking existing plugins.
The feature gate controls behavioral hook validation and runtime use.
Hooks-disabled validation remains green for plugins with optional hooks.
Invalid hook shape fails consistently.
Invalid hook behavior fails only when hooks are enabled.
Validation output distinguishes pass, fail, and skipped due to feature_disabled.
Docs explain the optional, gated behavior.
Repo closeout passes or any failures are documented with exact commands and output.
```

**Risk Notes**

The main implementation risk is accidentally making hook behavior required through schema validation. Keep `plugin_hooks` optional at the schema level, and keep missing hook files or disabled hook engines out of the failure path unless the feature gate is enabled.

The second risk is projection drift. Because AGENTS.md says to edit canonical sources, the plan should explicitly verify that runtime projections are regenerated from canonical plugin definitions rather than edited directly.

The third risk is ambiguous validation output. A skipped hook because the feature is disabled should be explicit, machine-readable, and separate from pass/fail, otherwise CI and agents will make bad assumptions later.
