**Change Frame**

Plan the change around one rule: the `Account` aggregate boundary decides what is allowed to mutate account state, and lifecycle ownership decides which implementation units must exist before dependents are changed.

That means implementation order should not start with callers, projections, UI, sync behavior, or convenience APIs. It should start with the canonical Account model and the domain operations that own its lifecycle transitions.

**Proposed Implementation Order**

1. **Confirm Account Language And Ownership**

   First, read the canonical domain language and path ownership docs:

   ```bash
   ./bin/ask repo doctor --json --robot
   sed -n '1,220p' UBIQUITOUS_LANGUAGE.md
   sed -n '1,220p' Docs/agents/14-path-ownership-boundaries.md
   sed -n '1,220p' Docs/agents/16-agent-operating-contract.md
   sed -n '1,220p' Docs/agents/04-validation.md
   ```

   Establish the exact answers to:

   - What is an `Account` in this repo’s language?
   - What entities or value objects are inside the `Account` aggregate?
   - Which lifecycle states exist?
   - Which component owns creation?
   - Which component owns activation, suspension, archival, deletion, or sync?
   - Which files are canonical sources versus runtime projections?

   Deliverable: a short implementation note with the approved Account lifecycle vocabulary and owner map.

2. **Define The Aggregate Boundary Before Touching Callers**

   Identify every place that directly mutates account-like state:

   ```bash
   rg -n "Account|account|accounts|owner|lifecycle|status|state|activate|suspend|archive|delete|sync" .
   ```

   Classify each hit as one of:

   - **Inside aggregate**: canonical Account state, invariants, lifecycle transitions.
   - **Application service**: coordinates a use case but should call Account behavior.
   - **Projection/runtime output**: derived from canonical source, should not own lifecycle rules.
   - **External adapter**: imports, exports, syncs, or renders Account state.
   - **Test/fixture/docs**: should encode expected behavior, not create a second rule source.

   Deliverable: a mutation inventory showing which writes must move behind the Account boundary.

3. **Implement Account Lifecycle Primitives First**

   Add or update the canonical Account aggregate APIs before changing higher-level workflows.

   The core should expose intention-revealing lifecycle operations, for example:

   ```text
   Account.create(...)
   Account.activate(...)
   Account.suspend(...)
   Account.archive(...)
   Account.restore(...)
   Account.delete/decommission(...)
   ```

   Exact names should follow existing repo language. The important part is that callers do not set raw lifecycle fields directly.

   Each lifecycle operation should enforce invariants such as:

   - required identity fields exist before activation
   - invalid state transitions are rejected
   - ownership cannot be reassigned except through an approved domain operation
   - archival/deletion rules preserve dependent data expectations
   - projection/sync state cannot drive canonical lifecycle state unless explicitly modeled as an import command

   Deliverable: Account lifecycle operations with focused unit coverage.

4. **Move Existing Mutations Behind The Boundary**

   Once the aggregate behavior exists, update application services and command handlers to call Account methods instead of directly mutating fields.

   Implementation priority should follow lifecycle ownership:

   1. Account creation path
   2. Activation/onboarding path
   3. Owner or membership changes, if inside the boundary
   4. Suspension/disablement path
   5. Archive/delete/decommission path
   6. Sync/import/export behavior
   7. Runtime projections and generated docs

   This order matters because later lifecycle operations depend on creation and activation semantics being stable.

   Deliverable: no direct lifecycle state mutation outside the Account aggregate or its approved repository/unit-of-work layer.

5. **Separate Lifecycle Ownership From Read Models**

   Runtime projections, docs, indexes, search surfaces, or generated skill metadata should consume Account state, not determine it.

   If a projection currently “fixes” or infers lifecycle state, move that logic either into:

   - the Account aggregate, if it is a domain invariant
   - an application service, if it is orchestration
   - a mapper/import policy, if it translates external data

   Deliverable: projections become downstream readers of canonical Account state.

6. **Update Tests In Domain Order**

   Test order should mirror ownership:

   ```text
   Account aggregate tests
   Application service tests
   Adapter/import/sync tests
   Projection/runtime output tests
   End-to-end or closeout validation
   ```

   Add tests for invalid transitions, not just happy paths. The most valuable cases are usually:

   - cannot activate incomplete Account
   - cannot archive already deleted Account
   - cannot mutate ownership from a projection/sync path
   - repeated lifecycle command is either idempotent or rejected, whichever the domain says
   - downstream projections update after canonical state changes

   Deliverable: tests prove the lifecycle owner, not only the final serialized shape.

7. **Regenerate Or Sync Derived Outputs Last**

   Because this repo distinguishes canonical sources from runtime projections, run projection or sync steps only after canonical Account behavior is correct.

   Candidate commands, adjusted once the exact handles are known:

   ```bash
   ./bin/ask skills explain <handle> --json --robot
   ./bin/ask skills prove <handle> --json --robot
   ./bin/ask repo closeout --changed --json --robot
   ```

   Deliverable: changed runtime artifacts, if any, are the result of canonical updates rather than hand edits.

**Suggested Task Breakdown**

1. **Discovery PR or commit**
   - Document Account aggregate boundary.
   - Document lifecycle ownership.
   - Inventory direct mutation sites.
   - No behavior change unless needed for tests.

2. **Domain PR or commit**
   - Add/update Account lifecycle methods.
   - Add invariant tests.
   - Keep adapters and projections mostly untouched.

3. **Application PR or commit**
   - Route command handlers/services through Account lifecycle methods.
   - Remove direct state writes.
   - Add use-case tests.

4. **Adapter/projection PR or commit**
   - Update import/export/sync/projection behavior to respect ownership.
   - Regenerate derived artifacts only from canonical sources.
   - Add regression tests for boundary violations.

5. **Closeout PR or commit**
   - Run repo validation.
   - Remove stale guidance or duplicated lifecycle rules.
   - Update docs where the aggregate boundary is now explicit.

**Definition Of Done**

The change is complete when these statements are true:

- There is one canonical Account lifecycle owner.
- Lifecycle transitions are represented as domain operations, not scattered field assignments.
- All external callers go through the aggregate or an approved application service.
- Runtime projections do not own Account lifecycle rules.
- Invalid lifecycle transitions are tested.
- `./bin/ask repo closeout --changed --json --robot` passes or produces only documented, understood failures.
- Any commit message created for the work ends with:

```text
Co-authored-by: Codex <noreply@openai.com>
```
