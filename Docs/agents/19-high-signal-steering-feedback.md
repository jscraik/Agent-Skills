# High-Signal Steering Feedback

Jamie steering is useful operating evidence. It does not automatically stop a
routine delivery lane or authorize new operating-system machinery.

## Routine Local Path

Finish the named outcome with the smallest local repair and the narrowest
existing proof. A routine correction does not require a papercut log, steering
ledger row, sibling census, Workforce admission, fan-in, or promotion receipt.
Keep local source proof separate from review, runtime, external, distribution,
and release claims.
The direct retry-stop and validation requirements in
[Workflow and Safety Guidance](/Docs/agents/13-workflow-and-safety-guidance.md) and
[Validation and Checks](/Docs/agents/04-validation.md) remain in force when the same
command fails twice; relaxing the selected system-improvement route does not
permit unchanged retries.

## Selected System-Improvement Route

Use this route only when Jamie explicitly requests it, or when at least one
of these conditions is true:

- the work crosses a security, privacy, credential, destructive, irreversible,
  external-commitment, release, or public-claim boundary;
- the same failure recurs in three independent tasks;
- two named active consumers require a contract that no existing surface can
  provide; or
- current executable contracts contradict one another.

First consider no system change, a local implementation repair, and an
improvement to an existing test, instruction, wrapper, or command. Do not add
a validator, schema, receipt, command, skill, workflow, or ledger entry merely
because feedback is high-signal or repeated within one lane.

When the route is selected, record the user outcome, named consumer, existing
mechanism considered, carrying cost, deterministic proof, and the surface
consolidated or replaced. The existing
`.harness/quality/steering-uptake.md` ledger and
`validate_steering_uptake.py` validator remain available for that selected
system-improvement work; they are not prerequisites for routine delivery.

## Stop Rule

Stop a routine lane only for a direct safety, privacy, secret, destructive,
external-commitment, or evidence boundary. Repeated feedback alone does not
create a stop rule. A Selected System Improvement may stop its own work until
its chosen existing mechanism has proof.

## Proof Before Proceeding

Routine work needs focused proof that the named change works. It does not need
a new receipt or steering artifact. A selected durable system improvement needs
proof that changes future behavior through its existing consumer surface.

## Scope Closure Authority

When Jamie asks for full implementation, do not silently relabel missing
acceptance criteria as follow-up work. Jamie explicitly approves that scope
change when narrowing is allowed. Whether Jamie explicitly approves that scope change
is part of the selected scope decision. Before reporting full implementation, run a
claim-vs-evidence closeout check that distinguishes completed requirements from
an explicit remaining blocker. A closeout caveat is evidence to classify, not
automatic authority to grow the operating system.

## Uptake Loop

For selected work, classify the feedback signal and root operational failure as
local or systemic, inspect relevant sibling patterns, and name the engineering
preference at stake: API philosophy, error-handling doctrine, runtime safety
assumption, or operational standard. Prefer an existing lint rule, schema
constraint, style rule, CI check, shared utility, reusable abstraction, or
architectural policy over a new surface. If a local implementation is not doing
what Jamie wants, use the smallest durable system improvement that serves its
named consumer.

Selected analysis may also record the runtime safety assumption, a schema constraint,
and evidence that an implementation is not doing what Jamie wants.

## Required Evidence

Selected work records the feedback signal, root operational failure, chosen
existing mechanism, durable system improvement, validation outcome, and any
explicit remaining proof. Ledger rows continue to use known taxonomy values
from the accepted list defined by
[`validate_steering_uptake.py`](/Infrastructure/scripts/validation-and-linting/validate_steering_uptake.py).
The `validate_steering_uptake.py` validator proves a chosen ledger entry; it
does not make routine work wait for one.

## Runtime-Handle Safety

Runtime-handle safety is a direct command-safety invariant, independent of the
selected route. Wait, poll, or resume only a live handle returned by the
immediately preceding tool result. Never probe a guessed, fabricated, stale,
or placeholder identifier. When there is no live handle, rediscover state with
a direct repository command. After invalid-handle use, continue with direct
commands until a new asynchronous call returns a live handle.

After any fabricated runtime handle is attempted, do not make another wait,
poll, or resume call until a new asynchronous tool result provides a live
handle. This direct safety rule does not create a steering-ledger requirement.

## Authority and Promotion Boundaries

Jamie Brain, SSM, and CO own intent, priorities, and cross-project constraints.
The Agent Skills OC and repository own project-specific discovery, technical
design, specifications, plans, implementation, and delivery. Jamie Brain
receives compact summaries and evidence pointers, not duplicate technical
artifacts.

Cloud, Tessl, runtime, review, publication, and release actions remain explicit
promotion decisions. Local evidence does not imply any of those claims.
