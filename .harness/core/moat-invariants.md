# Moat Invariants

Purpose: preserve what is actually defensible and stop protecting false sophistication.

## Proven Invariants

- Catalog size is not a moat.
- Plugin count is not a moat.
- Governance breadth is not a moat.
- The moat is agents remembering, routing, executing, validating, and improving real workflows.
- Outcome proof is the promotion mechanism for trusted capability.

## Strategic Assumptions

- Operational memory plus proof compounds.
- Deterministic orchestration compounds.
- Context compression compounds.
- Trust in `./bin/ask` compounds.
- Complexity without leverage weakens defensibility.

## Protect

- `./bin/ask` command contracts.
- Source/projection separation.
- Generated handle shallowness.
- Runtime budget and selection policy.
- `repo doctor` as first truth.
- Proof taxonomy and outcome evidence.
- Learned failures converted into commands, validators, evals, or memory.

## Do Not Protect

- Raw artifact volume.
- Giant command modules.
- Unproven plugin surfaces.
- Compatibility paths without expiry.
- Docs that merely repeat live command output.
- Skill breadth without routing quality or proof.

## Forbidden Regressions

- Structural audit called outcome proof.
- Invocation counted as usefulness.
- Catalog growth presented as strategic progress.
- Complexity defended because it looks sophisticated.
