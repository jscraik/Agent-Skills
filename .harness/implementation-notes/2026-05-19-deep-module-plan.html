Deep Modules as Agent Control Boundaries

Plan for converting agent-skills toward stable public interfaces, hidden implementation depth, SDK-grade contracts, and seam tests that let agents work inside modules without leaking risk into callers.

Legend

Canonical source: product behavior, skills, docs, decisions.
Command surface: stable CLI/topic/action interface.
Deep service module: hidden implementation and adapters.
Runtime projection: generated surface, never hand-edited.
Proof gate: boundary tests or production-like tracer.

Read The Plan

1. Keep behavior owned by source repos

Skills, plugin packages, references, and eval cases stay in canonical source paths. Shared machinery should not absorb product judgment.

2. Keep RF-1 narrow

The live SDK wedge is JSC-329: register and prove ./bin/ask skills doctor context7 --json --robot before broader module reshaping. RF-1 is additive over skills prove and skills proof.

3. Make doctor the first deep module

Doctor should expose a stable SDK contract while readiness checks, precedence, and next-command logic stay hidden behind it.

4. Mark safe only with seam proof

A module is agent-safe only when the interface is stable and a boundary test locks caller-visible behavior. For doctor that means schema validation, action parity, and a second skill fixture beyond context7.

5. Keep docs thin

Machine-readable contracts, fixtures, evals, lifecycle events, and harness consumer tests are the source of truth. This visual is only a map over those artifacts.

6. Let evals teach

Eval outcomes should produce classified improvement deltas, bounded source changes, rerun proof, and promotion or rollback evidence so skills get better through use.

7. Spin the terminology flywheel

Repeated patterns from use and evals become controlled SDK terms in command JSON, schemas, fixtures, eval labels, package metadata, and harness reports.

Extracted SDK Guidance

API first, implementation second

The SDK boundary starts with a stable contract that developers and LLMs can call predictably. For this repo, the first contract is data.skill_doctor, not an internal folder move.

Less caller code is better

Great SDKs remove authentication, defaults, error mapping, retries, logging, and observability burden from the caller. ASK should return typed next actions instead of making agents infer repo state from raw files.

Compatibility is a product feature

Public JSON shapes, handle names, package metadata, and status precedence need deprecation and diff checks before generated emitters or broad refactors are safe.

Language Runtime Choices

TypeScript: Effect

If the SDK core or emitters move into TypeScript, use Effect for typed effects, dependency layers, structured errors, schedules, streams, schema validation, and OpenTelemetry integration.

Python: uv

Python SDK/runtime work should use uv for reproducible execution, dependency locking, and validation command surfaces instead of ad hoc virtualenv or package-manager assumptions.

No framework takeover

The SDK should be invoked by users and agents. It should not become a framework that forces every consumer project into one architecture before it can use skills safely.

Codex Runtime Lessons

Package Builder

Import the Codex package-builder shape: deterministic layout, metadata, target rules, archive inspection, and validation. Use it after RF-1 for skills package-doctor.

Lifecycle Proof

Subagent, tool, hook, package, projection, and eval activity should emit structured events so evals can assert behavior instead of trusting final prose.

Namespaces + Search

Follow upstream Codex: avoid flat global tools. Keep skills, plugins, harness, evals, review, and release surfaces namespaced and discoverable through search.

Enablement State

Installed, projected, enabled, valid, discoverable, routable, and smoke-tested are separate SDK states with separate evidence.

Permissions + Context

Permission profiles should use canonical deny. Every run should classify local, optional-local, remote, CI, app-server, or unknown execution context.

Provenance + Upgrades

Reports should preserve skill, package, plugin, and source identity. Package upgrades stay additive unless a migration explicitly removes capability.

Local Evidence Services

Like the observability image, signals should fan out locally into queryable evidence. Codex can then correlate failures, patch the owner module, rerun the workload, and improve the skill through eval feedback.

Logs Command output, hook output, validation text, blocker strings.
Metrics Pass/fail counts, retry counts, duration, freshness, fixture drift.
Traces Command lifecycle, tool lifecycle, package lifecycle, projection lifecycle, subagent lifecycle.
Query + Correlate Read collector outputs through an evidence-provider seam, find the failing boundary, classify ownership, and choose the smallest source change.

Promote / Roll Back Skill improvement lands only with rerun proof and a promotion or rollback decision.

Live SDK Wedge

Linear: JSC-329 / RF-1

Active execution handle: register and harden the skills doctor contract fixture for context7. Status is Triage; project assignment is intentionally omitted until the healthy destination is confirmed.

Implementation blockers

The north-star strategy, apparatus lens, and doctor schema are now present. The live CLI still does not register skills doctor or skills package, so RF-1 begins with command registration and action-parity evidence.

Public SDK Interface

./bin/ask skills doctor context7 --json --robot is the intended first trusted SDK boundary. Today it exits at parser level with invalid choice, so the first proof is replacing that failure with data.skill_doctor. Callers should depend on that payload, not skill internals or package source shape. The payload schema is Infrastructure/config/schemas/skill-doctor.v1.schema.json.

Conversion Sequence

1 Doctor command + fixture

Register skills doctor, then harden data.skill_doctor for context7: required fields, status precedence, and safe next_command.

2 Negative-path matrix

Cover contradictory readiness states after RF-1 proves the baseline contract and fixture ownership.

3 Package-doctor seam

Add skills package-doctor <skill> for metadata, layout, namespace, permission, enablement, provenance, and package evidence.

4 Lifecycle and compatibility

Add lifecycle-event assertions, additive upgrade gates, surface diffs, and schema checks before generated outputs expand.

5 Emitters and runtimes

Introduce package, docs, eval, plugin, and Linear emitters over the same contract IR. Use Effect for TypeScript and uv for Python lanes.

First PR Shape

Change

Add the skills doctor command seam, then add focused doctor fixture/snapshot coverage for context7 and one non-context7 skill class. Preserve namespace-first ./bin/ask skills ... --json --robot behavior while making the SDK contract explicit.

Compatibility rule

Preserve data.skill_doctor shape, blocker and warning separation, runtime/package/outcome-proof distinction, status precedence, and next_command semantics. Parser actions, help output, metadata, and guided errors must expose the same action set.

Agent-safe result

Before RF-1 passes, the doctor boundary is risky: the interface is planned but unregistered. After RF-1, agents can rely on doctor as the first SDK readiness boundary because the interface and seam tests both exist.
