# Document Types

Use this reference when you need to classify or restructure a documentation page before drafting.

## Primary rule

Pick one dominant document type per page. If the draft needs more than one type, split the page or keep the main type in the page and cross-link the rest.

## Tutorial

- Use when the reader is new and needs to learn by doing.
- Trigger signals:
  - "teach me"
  - "walk me through"
  - "first time"
  - "getting started"
- Recommended shape:
  - goal
  - prerequisites
  - numbered steps
  - expected result after each major step
- Success check:
  - a beginner can complete it end-to-end without outside help

## How-to Guide

- Use when the reader already knows the basics and needs to complete a task.
- Trigger signals:
  - "how do I"
  - "set up"
  - "deploy"
  - "migrate"
  - "configure"
- Recommended shape:
  - task statement
  - assumptions
  - numbered steps
  - verification
- Success check:
  - an experienced reader can complete the task without backtracking

## Reference

- Use when the reader needs facts, options, flags, schema, or parameter lookup.
- Trigger signals:
  - "what are the options"
  - "API"
  - "flags"
  - "schema"
  - "parameters"
- Recommended shape:
  - consistent entry format
  - defaults
  - constraints
  - small examples
- Success check:
  - a reader can find a specific fact in under 30 seconds

## Explanation

- Use when the reader needs rationale, concepts, or tradeoffs.
- Trigger signals:
  - "why"
  - "how it works"
  - "tradeoffs"
  - "architecture rationale"
- Recommended shape:
  - context
  - core concept
  - tradeoffs
  - alternatives
- Success check:
  - a reader can explain the rationale in their own words

## Mixing Types

- Do not bury reference tables inside tutorials.
- Do not hide conceptual rationale inside task steps.
- Do not turn explanation pages into setup checklists.
- If a README mixes types, keep the dominant onboarding path in the README and link out to task guides, reference pages, and explanations.
