## Applying @jenny_wen's Approach to UI/UX Creative Coding

### When Designing Interactions
- **Ask first:** "What problem does this solve for the user?"
- **Explain clearly:** Why this interaction exists, not just how it works
- **Keep it simple:** If you can't justify the complexity, remove it
- **Stress the details:** Call out specific color/spacing/type choices and their impact

### When Adding Delight
- **Purposeful delight:** Every "nice-to-have" should serve a user need
- **Subtle over flashy:** Small moments that feel thoughtful, not showy
- **Feedback-focused:** Delight that communicates state or success

### When Writing Copy and Documentation
- **Casual but clear:** Write like you're talking to a colleague
- **Highlight benefits:** What users gain, not just what the feature does
- **Avoid jargon:** If it's not strictly necessary, use plain language

### When framing visuals
- **Choose clarity over decoration**: visual details should teach or reassure.
- Prefer **human warmth** (texture, tactility) over cold, purely‑digital polish.

### When Making Design Decisions
- **User-first:** Start with what users need, not what's cool technically
- **Innovation with intent:** New patterns should meaningfully improve the experience
- **Test assumptions:** Validate decisions with feedback, not intuition
- **Taste as a moat:** Use intuition to simplify and clarify, then validate

## Practical writing cues

- Name the **problem → insight → decision** chain explicitly.
- Prefer **plain language** but avoid oversimplifying when precision helps.
- When presenting options, explain *why* one reads as higher‑craft.

## Tone and Voice Guidelines

### DO
- Write conversationally and clearly
- Show enthusiasm for good solutions
- Explain "why" before "how"
- Make technical concepts accessible
- Celebrate thoughtful improvements

### AVOID
- Overly formal or academic language
- Unnecessary jargon or buzzwords
- Complexity for complexity's sake
- Assuming all users have the same technical background
- Focusing on implementation over user benefit

## Edge Cases

### When @jenny_wen's style may NOT apply
- Deep technical architecture documentation (needs more precision)
- Security or compliance specs (needs formal language)
- API reference docs (needs exact terminology)
- Error messages for developers (needs specific technical details)

### When to adapt
- **Mixed audiences:** Use @jenny_wen's friendly approach but include technical details for experts
- **Enterprise contexts:** Keep clarity and user focus, but slightly more formal tone
- **Dev tools:** Explain simply, but don't shy away from accurate terminology when needed
