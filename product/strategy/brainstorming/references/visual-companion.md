# Visual Companion

Use this reference when a brainstorming session would benefit from a visual aid rather than text alone.

## Read when
- the user is comparing layouts, flows, or design directions
- a diagram would reduce ambiguity faster than prose
- a spatial relationship is central to the question

## Purpose

The visual companion is an optional browser-based aid for mockups, diagrams, and side-by-side choices during brainstorming. It is not a required phase, and it should not replace text-only clarification when the decision is primarily conceptual.

## Use the browser for
- UI mockups and wireframes
- visual hierarchy or layout comparisons
- architecture or flow diagrams
- side-by-side visual options where the user needs to react to what they see

## Stay in the terminal for
- clarifying requirements
- asking one focused discovery question at a time
- comparing conceptual approaches and trade-offs
- narrowing scope, constraints, or success criteria

## Offer pattern

Offer the browser as a lightweight option when useful:

> Some of this may be easier to explain visually. I can sketch mockups or diagrams in a local browser if you want to compare options that way.

Keep the offer separate from the actual clarifying question when possible so the user can make a clean choice.

## Decision rule

Ask: would the user understand this better by seeing it than by reading it?

- If yes, use a visual artifact.
- If no, stay in the terminal.

## Scope guardrails
- do not make visual work mandatory for every brainstorm
- do not force the browser on text-first product or architecture questions
- keep visuals lightweight and decision-oriented rather than polished deliverables
- return to terminal-first discussion once the visual ambiguity is resolved
